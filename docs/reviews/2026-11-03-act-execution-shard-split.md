# act-execution shard split — measured on the 16 GB single-channel box (2026-11-03)

Follow-up to [2026-10-27-maven-loop-audit.md](2026-10-27-maven-loop-audit.md), whose numbers were taken
on the previous daily (i5-8400, 6C/6T). This one measures the new daily and splits the module that the
previous sharding left as the hard floor.

Everything here was measured at `e0ad2d0c` on **Happy**: Intel i5-12500 (6C/12T), 16 GB DDR5 running in
**one channel** (1×16 GB in a 2-DIMM board), Samsung 870 EVO SATA SSD for `D:`, Windows 10 19045.
`~/.m2/repository` is warm (546 MB), so every run below used `mvn -o`.

## 1. Why act-execution was the thing to split

`shard 3` and `shard 4` on this box both finished in ~115-118 s, and the reason was visible in the
serial `clean test` reactor summary (measured at `e0ad2d0c`, one process, idle box, `Total time 03:17`):

| module | reactor time | sum of its classes | classes | tests |
|--------|-------------:|-------------------:|--------:|------:|
| act-execution | 85.0 s | 76.8 s | 111 | 1130 |
| act-app | 39.0 s | 34.5 s | 23 | 74 |
| act-common | 18.3 s | 8.7 s | 16 | 124 |
| act-knowledge | 16.9 s | 13.4 s | 25 | 263 |
| act-aria | 12.0 s | 9.1 s | 24 | 180 |
| act-agent | 10.0 s | 5.7 s | 20 | 293 |

| act-mcp | 7.1 s | 4.0 s | 17 | 172 |

Module-level lanes are indivisible, so no lane could ever be shorter than act-execution. Splitting it
was the only way to move the floor; the target was act-app's ~39 s.

## 3. The committed partition

[scripts/lanes/act-execution/g1.txt](../../scripts/lanes/act-execution/g1.txt) … `g4.txt`, generated by
`node scripts/lane-plan.mjs gen act-execution 4` — longest-processing-time over the measured costs, so
each of the three heavy classes lands in a different fragment:

| fragment | cost | classes | tests | heaviest class in it |
|----------|-----:|--------:|------:|----------------------|
| g1 | 17.21 s | 24 | 232 | `CoreExecutionServiceSandboxLaunchAbortTest` 10.1 s |
| g2 | 17.21 s | 24 | 212 | `OpenCodeCoreSessionTest` 10.1 s |
| g3 | 17.21 s | 24 | 308 | `CoreProgressPumpTest` 9.2 s |
| g4 | 17.21 s | 36 | 313 | `DeferredRunStopPendingStopSliceTest` 4.6 s |

4 fragments because 4 is the widest local fan-out the script accepts; a lane can take any subset, so one
committed partition serves K=1..4 instead of four hand-maintained lists. Each file is a surefire
**includes file** (one FQCN per line, `#` comments ignored), so the partition is a list of class names in
the repository, not a `-Dtest` pattern somebody retypes.

`node scripts/lane-plan.mjs plan K` then packs the 4 fragments together with the whole modules and
writes each lane's **complete** class list plus `target/mvn-lane/plan.json`. `scripts/mvn-lane.sh` holds
no weight of its own any more: the old `WEIGHTS` table (measured on the previous box) is gone, and the
timing class list is now discovered from `@Tag("timing")` in the sources instead of a hardcoded name
list, so a fifth tagged class cannot be forgotten.

## 4. Mechanism: a lane runs `surefire:test` as a goal, never as a phase

Two lanes writing one module's `target/` is the hazard this split creates, and it is not theoretical:
`mvn test` re-enters `process-resources`, `compile` and `test-compile`, and maven-compiler's incremental
decision is made by two processes at once, which can both decide to rewrite the same `.class` files.
So a shard lane invokes the plugin goal directly:

```
mvn -o -B -pl <modules> surefire:test -Dsurefire.includesFile=<lane list> -DtempDir=lane<i> \
    -Dtest.argline.base= -Djacoco.skip=true -DexcludedGroups=timing -Dspring.profiles.active=h2
```

No lifecycle phase runs, so nothing compiles; the shared `install -DskipTests` immediately before it
produced the classes and the test resources. `inner` and `timing` invoke the same goal (with
`test-compile` ahead of it, since a developer may have just edited code) for a different reason - see the
coverage Minor in section 12. Verified from the spike log: the goal-only invocation
printed only `--- surefire:3.5.3:test (default-cli) ---` and no `Compiling` line, and the pom's
`**/*IntegrationTest.java` excludes still held (a listed `MaintenanceControllerIntegrationTest` was not
run), as did `-DexcludedGroups=timing` (a listed `OpenCodeCoreAdapterTest` was not run).

Two things this uncovered, both now documented in the files they touch:

- **`@{argLine}` is not survivable without JaCoCo.** Goal-only means `jacoco:prepare-agent` never runs,
  so the pom's `<argLine>@{argLine} --enable-preview …` reached java as a literal and the fork died with
  `Error: could not open '{argLine}'` — the same failure the pit profile already works around.
  `-DargLine=` does **not** fix it: surefire's late replacement reads project properties, and a CLI `-D`
  is a user property. The fix is the new `${test.argline.base}` property
  ([agent-control-tower/pom.xml:53-58](../../agent-control-tower/pom.xml#L53)), which defaults to
  `@{argLine}` and is therefore inert for every normal build. Positive control that it stayed inert:
  `mvn-lane.sh gate act-mcp` after the change logs `argLine set to -javaagent:…org.jacoco.agent…`,
  writes a 189,902-byte `target/jacoco.exec` that the lane had just deleted, and reports
  `Analyzed bundle 'ACT MCP' with 24 classes`.
- **`includesFile` is a property of the Maven process, not of the module.** A lane that lists only
  act-execution's fragment would apply that file to *every* module it builds and run nothing else. So a
  lane's file spells out its whole class list. That is also why the planner, not the shell, owns the
  lists.

## 5. Discovery had to learn what surefire actually does

The guard's first draft keyed on **file names** (`**/*Test.java` etc.) and produced 110 classes for
act-execution where the run produced 111 reports. Two real defects:

- `PackCredentialCipherPropertyTest` is a jqwik `@Property` class with no `@Test` — fine for a file-name
  rule, but it was being missed by an annotation-shaped filter. Removed.
- `act-app/src/test/java/io/aria/conductor/app/dev/DevSqlControllerProfileTest.java` declares a
  **second top-level class** `DevSqlControllerH2ProfilePresenceTest`. Surefire scans
  `target/test-classes` and matches the *class* name, so that class really does run — and it is the
  heaviest class in act-app (12.95 s, 37 % of the module). A file-name rule would have dropped it from
  every lane, and nothing else would have noticed.

`shardableClasses()` now enumerates top-level `class` declarations (skipping `abstract`, since surefire
cannot run one, and skipping nested types, which run with their outer class) and reads `@Tag("timing")`
from the declaration's own annotation window rather than from the whole file, so a tag on one class in a
two-class file cannot mark the other.

## 6. Guards, and the mutants that prove them

`node scripts/lane-plan.mjs check` runs before Maven starts (`scripts/mvn-lane.sh:shard`) and fails on:
a discovered shardable class in no fragment (`MISSING`), a class in two (`DUPLICATE`), a listed name with
no such class (`STALE`), a class the measured run produced but discovery cannot see (`UNDISCOVERED`), a
fragment whose `# cost=` header no longer matches its contents (`STALE COST`, catches hand-edits), and a
module that has test sources but no measured costs (it would run in no lane and the arithmetic would
still balance, because the arithmetic is measured from the same table).

`node scripts/lane-plan.mjs verify <timing.log> <lane logs…>` reads `plan.json` back and fails after the
run if a planned class the measurement has seen run printed no result line, a lane ran a class it was not
given, one class ran in two lanes, a `@Tag("timing")` class ran inside a lane (i.e. `excludedGroups`
silently not taking), or - the oracle added in the review round of section 12 - a class compiled into
`target/test-classes` that matches surefire's includes was given to no lane. It prints the number of
compiled classes it examined (248) so a skipped oracle can never be read as a passed one.

Severity is split by what is actually at stake: anything that would silently lose or duplicate work is
fatal, and anything that only makes the *balance* stale is a warning. A class the measurement has seen
run but that printed no result line is fatal; a class with no measured history at all (added since, or a
helper named `*Test` that surefire produces no report for) warns and lets the run stand, because the lane
was still given it.

All three guards were mutated to prove they fire, not just to prove they pass. The last five rows were
re-run against the surviving K=4 lane logs at `4fb16ea7`, so they are reproducible from a committed tree
plus one run of the lane (section 10), and section 12 pairs two of them against `64e8d6e0`'s own copy of
the script to show what the older guard did with the same input.

| mutant | observed | exit |
|--------|----------|-----:|
| delete `PackCredentialCipherPropertyTest` from g3 | `MISSING … (in no fragment - it would never run. Remedy: node scripts/lane-plan.mjs gen act-execution, …)` plus `STALE COST … g3.txt header says 17.21s but its classes cost 16.78s` | 1 |
| add one class to two fragments | `DUPLICATE … GitBranchServiceTest listed 2 times` plus `STALE COST … g2.txt … 17.51s` | 1 |
| add a name with no such class | `STALE … DoesNotExistTest (listed but no shardable test class by that name exists)` | 1 |
| add a real new test source (`ZZProbeNewTest.java`) | `MISSING io.aria.conductor.execution.ZZProbeNewTest`, so `shard` refuses to start Maven; after `gen` the class is in g4 (packed at 0 s) and `check` is clean | 1 → 0 |
| delete that source and `gen` again | the four fragment files come back **byte-identical** to the committed ones | — |
| drop one class from `plan.json` | `lane1 ran 1 class(es) it was not given: EXTRA …H2ProfileConfigurationTest` | 1 |
| invent a never-measured class in `plan.json` | `lane1 also listed 1 class(es) never seen in a measured run, which produced no report: …` | 0 |
| drop `PackCredentialCipherPropertyTest` from lane4 in `plan.json` | `EXTRA io.aria.conductor.execution.credential.PackCredentialCipherPropertyTest` **and** `… is compiled into act-execution/target/test-classes and matches surefire's includes, but no lane was given it and it is not tagged timing - it ran in no lane`, then `failed (2 problem set(s))` | 1 |

| unmutated | `exact cover OK - 108 shardable classes, 4 fragments` and `verify: exact cover across lanes, and the test total equals the measured single process` | 0 |

The compiled-oracle row is the one that matters. The three oracles are complementary, not redundant: source
discovery (`check`, before Maven) is the only one that can refuse a bad partition *before* spending 75 s;
the printed `-- in` lines (`verify`) are the only ones that prove a class actually executed; the compiled
`target/test-classes` enumeration is the only one that can see a class the other two are blind to, because
both of them are filtered through what the planner already thought of. It costs the passing lane one
directory walk per module (`javap` runs only on the failure path), so the guarantee is not paid for twice.

## 7. Completeness arithmetic, per K

Class cover is *enforced*; the arithmetic is *reported*. That split is deliberate and came out of the
review round (see the last two mutants above): `sum(lanes) + timing == the single-process total` is a
statement about a snapshot taken at `e0ad2d0c`, so treating it as a gate would turn one added `@Test`
method into a red daily lane and a 199 s re-measurement. What must never drift silently is which *classes*
ran, and that is what fails the run.

With that said, every run below does add up exactly (all rc=0, same 8 skipped):

| K | per-lane `Tests run` | lanes | timing lane | total | measured single process | skipped |
|---|----------------------|------:|------------:|------:|------------------------:|--------:|
| 2 | 776 + 1480 | 2256 | 70 | **2326** | 2326 | 8 = 8 |
| 3 | 486 + 975 + 795 | 2256 | 70 | **2326** | 2326 | 8 = 8 |
| 4 | 241 + 635 + 768 + 612 | 2256 | 70 | **2326** | 2326 | 8 = 8 |

Class counts close the same way: 244 classes planned = 248 measured − 4 tagged timing, and `plan` refuses
to emit a table where a class is in two lanes.

The K=4 row is the one that survived to `4fb16ea7` and was re-verified there after the guards changed,
against the committed fragments and the compiled oracle; K=2 was then re-run at `97279dc3`, so all three K
values are proven at a commit this branch delivers (the markdown-only commits after it change no lane):

```
verify: lanes ran 241 + 635 + 768 + 612 = 2256, timing lane 70 (the tagged classes hold 70),
        total 2326 vs the measured snapshot's 2326          # K=4 at 4fb16ea7
verify: lanes ran 776 + 1480 = 2256, timing lane 70 (the tagged classes hold 70),
        total 2326 vs the measured snapshot's 2326          # K=2 at 97279dc3
verify: skipped=8 (the measured run skipped 8) and failures+errors=0
verify: compiled oracle saw 248 surefire-matching class(es) under target/test-classes from D:\wt\lane-bench,
        every one given to a lane or tagged timing
verify: exact cover across lanes, and the test total equals the measured single process
```

The K=3 arithmetic at `4fb16ea7` came from the run reported in section 12 (`486 + 975 + 795 + 70 = 2326`).
`plan 2` is byte-identical between `64e8d6e0` and `4fb16ea7` - compared by running both versions of the
script against the same tree - and nothing after `4fb16ea7` touches the planner or the partition (`git
diff --name-only 4fb16ea7..HEAD` is `AGENTS.md`, this file and `mvn-lane.sh`, and every one of that script's
changed lines is a comment), which is why the same 776 / 1480 split appears in both runs.

## 8. The measured curve, and where the box gives up

Same lane phase, same committed partition, one reactor at a time, box idle. "lane phase" is the total
minus the serial timing lane. `shard total wall` starts its clock *after* the shared
`install -DskipTests` (4.2-4.5 s once the repository is warm, 21.2 s into a cold private repo), and the
previous sweep's numbers were produced the same way, so the comparison holds.

| run | lanes wall | timing | shard total |
|-----|-----------:|-------:|------------:|
| serial `clean test` (reference) | 199 s | — | **199 s** |
| `shard 2` (module-only packing, previous sweep) | ~83 s | 20.2 s | 103.2 s |
| `shard 3` (module-only packing, previous sweep) | ~97 s | 21.1 s | 118.4 s |
| `shard 4` (module-only packing, previous sweep) | ~90 s | 24.7 s | 115.0 s |
| **`shard 2` (act-execution split)** | 78.1 s | 18.3 s | **96.4 s** |
| **`shard 3` (act-execution split)** | 62.7 s | 18.6 s | **81.3 s** |
| **`shard 4` (act-execution split)** | 59.8 s | 18.5 s | **78.3 s** |
| **`shard 3` again, from a fresh checkout at `ebcf14c7`** | 65.5 s | 20.8 s | **86.3 s** |
| **`shard 3` at the branch tip `70e89ad9`** | 62.2 s | 18.4 s | **80.6 s** |
| **`shard 3` at `4fb16ea7`, twice** | — | — | **78.5 s / 79.8 s** |
| **`shard 4` at `4fb16ea7`** | 56.7 s | 18.0 s | **74.7 s** |
| **`shard 2` at `97279dc3`** | 75.9 s | 17.9 s | **93.8 s** |

The baselines and the previous-sweep rows were measured at `e0ad2d0c`. The three rows that say only
`(act-execution split)` ran from the working tree that became `ebcf14c7` (same scripts, pom and fragments as
that commit); every row that names a SHA is a fresh `git checkout` of it, which also confirms the lane script
behaves on a Windows checkout where git hands it over with CRLF line endings. The two `shard 3`
cells at `4fb16ea7` have no lane split because all runs write to one log directory and the K=4 run that
followed overwrote them; the totals are the script's own summary lines, and the K=4 lane phase is the
total minus that run's retained `timing` line (18.0 s), which is how the column is defined.

The five K=3 runs are the honest spread: identical lane work (486 + 975 + 795 in every run whose counts
were retained), 7.8 s between best and worst, a good part of it in the serial timing lane (18.0-20.8 s
across all runs). Treat the totals as ±5 s, and the class cover as exact.

So the split is worth 6.8-9.4 s at K=2, 32.1-39.9 s at K=3 and 36.7-40.3 s at K=4; against the serial suite
that is 2.12x at K=2, 2.31-2.54x at K=3 and 2.54-2.66x at K=4. The floor is no longer act-execution: at K=4
the heaviest planned lane is act-app + act-mcp at 38.5 s, exactly the target this split was aimed at.

**The curve flattens because of memory bandwidth, not cores.** At K=4 the four lanes ran 50.2, 56.0,
57.8 and 57.4 s (`Total time` from each lane log) against planned costs of 38.5, 39.0, 36.3 and 35.0 s —
11.7 to 22.4 s of inflation per lane, and the *order inverted*: the heaviest planned lane (38.5 s) finished
first at 50.2 s while the lightest (35.0 s) came in second-slowest at 57.4 s. The run at `4fb16ea7`
reproduced the shape (46.1, 52.9, 54.7, 54.3 s against the same plan, 7.6-19.3 s of inflation) though not
the level, and again the heaviest went first and the lightest finished second-slowest - 0.4 s off the
bottom in both runs. All four finished within 7.5 s of each other both times, which is what a shared
bottleneck looks like. A sampler every 2 s over the first K=4 run recorded free RAM falling
from 5,543 MB to **2,826 MB** at the 50 s mark (of 15.75 GiB usable), i.e. the four lanes took ~2.7 GB.
K=4 is reachable on this box, but it costs the headroom a browser and an IDE want.

Against five K=3 runs (78.5-86.3 s) the two K=4 runs (74.7, 78.3 s) gain 0.2-11.6 s: the samples do not
overlap, but only by 0.2 s at the closest edge, so the honest statement is "a few seconds, worth it only
when nothing else is running". Guidance in `scripts/mvn-lane.sh` therefore says K=3 by default, K=4 when
the box is otherwise idle.

One caveat on the predictor itself: planning by summed per-class cost is a *ranking*, not a forecast. The
cost of a class depends on which contexts its lane already booted (measured: `RunCoreLogTest` took 4.09 s
inside the 111-class module run and 11.69 s alone in a cold fork, because its `awaitContent()` poll waits
on a drain thread that the rest of the process had already warmed). Do not read the planned cost column as
a promise; the post-run `verify` is what is actually guaranteed.

The 32 GB sibling machine (i7-8700, 6C/12T) is **not reachable from this session** — no route was
provided and this agent runs on Happy only — so no number is claimed for it. Expectation, labelled
INFERRED: with ~16 GB more headroom the K=4 lane phase should approach its planned ~39 s instead of
~58 s, which would put `shard 4` near 58-60 s total; that is a memory-bandwidth and page-cache guess,
not a measurement. The 12.95 s `DevSqlControllerH2ProfilePresenceTest` inside act-app is the next floor
on any machine.

## 9. What this does not fix

- The serial timing lane is now 17.9-20.8 s, i.e. 24 % of the best K=4 total. It is serial on purpose;
  shortening it means making those four classes not bound wall time, which is a test-design change.
- act-app is the new indivisible task (34.5 s class-sum, 23 classes) with 37 % of it in one class. The
  same fragment treatment applies, and `lane-plan.mjs gen act-app` will do it, but it has not been
  measured here and is deliberately not shipped unmeasured.
- Coverage is still off in every shard lane (`-Dtest.argline.base=` plus `-Djacoco.skip=true`); the
  ratchet still only gets enforced by `gate`, and `gate` still deletes `target/jacoco.exec` first.
- `forkCount` stays 1. Nothing in this change touches the pom's fork settings; the four wall-clock
  classes are quarantined instead.
- The hosted lane is unchanged: `.github/workflows/ci.yml` still runs four module groups on four
  runners, and `e2e/agent-core/ci-contract.test.mjs` still asserts those command strings. Nothing here
  alters CI behaviour.

## 10. Reproduction

```bash
cd D:/project/aria-conductor/.qoder/worktrees/perf-test-lane-sharding
node scripts/lane-plan.mjs check                       # guard, no Maven
node scripts/lane-plan.mjs plan 3 <dir>                # writes laneN-includes.txt + plan.json

MVN_REPO=<copy of ~/.m2> bash scripts/mvn-lane.sh gate act-mcp   # JaCoCo positive control
```

`MVN_REPO` is a copy (`cp -r ~/.m2/repository D:/wt/m2-lanebench`, 3 s) rather than the shared repo:
the lane's `install -DskipTests` writes `act-*.jar` into whatever repository it is pointed at, and a
scratch branch should not overwrite the SNAPSHOT jars the developer's own tree resolves against. The
per-class table in `scripts/lanes/measured-costs.json` was produced from the serial run's
`-- in` lines; `node scripts/build-metrics/summarize.mjs <module> <log>` regenerates the same view from
any module log.

## 11. INFERRED list

- The 32 GB expectation in section 8 — no route to that machine, nothing measured.
- That memory bandwidth (not CPU, not disk) is the single cause of the K=4 flattening. Evidence is
  circumstantial: 12 threads, only 6 physical, 4 lanes finishing within 7.5 s of each other, 2.8 GB free
  at the worst moment, and one DIMM. A per-cycle stall counter would be needed to call it proven.
- That `--enable-preview` is still reaching the forked JVM in goal-only lanes. Strong indirect evidence
  (all 2,256 lane tests pass, and a preview-compiled class would refuse to load without it) but the fork
  command line was not captured for a lane.
- That `abstract class` declarations named `*Test` do not produce report lines. Not observed in this
  repository's current set; the rule is there to keep discovery honest if one appears.
- That the `CoreProgressPumpTest` failure reported in section 13 is caused by the mechanism named there.
  The mechanism is read off the code and the assertion's shape; it was not reproduced on this box.

## 12. Independent review round (`e0ad2d0c..64e8d6e0` → `4fb16ea7`)

A read-only reviewer audited the shard-split range and returned **REQUEST CHANGES**: two MAJORs and four
Minors, three of which were fixed and one declined. A fifth item came from self-review. Every finding was
reproduced against the code or a real log before it was acted on. No test was relaxed, no scenario deleted,
no timeout widened, and no product or test source is in the range at all (`git diff --name-only
e0ad2d0c..4fb16ea7` returns no `src/` path). `scripts/lanes` has exactly one commit in the range - `ebcf14c7`,
which created the four fragments and the cost table - and nothing later touched it, so the fragments the
K=2/3/4 rows were measured against are byte-for-byte the fragments `4fb16ea7` ships and the timings stay
comparable across the two SHAs. The one thing this round did
loosen is the arithmetic gate, and section 7 states why a snapshot cannot be a gate and what enforces
completeness instead.

**MAJOR 1 - `verify` gated on arithmetic that cannot stay fresh.** It compared the run's test total against
the frozen snapshot, so adding a single `@Test` method anywhere made every green lane print
`completeness LOST - 2327 != 2326` and demanded a 199 s re-measurement to unblock an unrelated change.
Completeness is a property of *classes*, so `verify` now enforces classes and *reports* the arithmetic
(`NOTE the test total moved … It is NOT a completeness failure`, exit 0). Before and after, same input -
one module's `Tests run: 172` bumped to 173 in a copy of the real lane1 log, nothing else touched:

```
64e8d6e0 (before): completeness LOST - 2327 != 2326. No lane may be trusted until this adds up.   rc=1
4fb16ea7 (after):  NOTE the test total moved (2327 vs the 2326 measured at e0ad2d0c). … It is NOT
                   a completeness failure.                                                        rc=0
```

**MAJOR 2 - a class could run in no lane and the run would still be green.** `check`'s oracle is *source*
discovery: any way a class escapes that regex (declaration sharing a line with its annotation, a record, a
second top-level type in one file) also escapes the guard, and `verify`'s planned-vs-ran comparison only
iterates names somebody already planned. Both were real blind spots, not hypothetical - section 5 documents
two classes the file-name oracle missed. The fix is to consult the oracle surefire itself uses: after the

## 13. The one hosted failure, and why it is not this branch's

`Java Unit Tests (execution)` went red once, at `97279dc3` (run 41668405877):

```
[ERROR] Tests run: 34, Failures: 1, Errors: 0, Skipped: 0 -- in io.aria.conductor.execution.runtime.progress.CoreProgressPumpTest
org.opentest4j.AssertionFailedError: [a halted pump does not even read the message list]
expected: 4  but was: 5
    at CoreProgressPumpTest.aDrainAfterStopEmitsNothingAndPerformsNoPoll(CoreProgressPumpTest.java:1133)
```

**The branch cannot have caused it.** `git diff --name-only e0ad2d0c..97279dc3` contains no `src/` path at
all, and that test file was last touched by `605ecbba` (2026-10-26, PR #114). `.github/workflows/ci.yml` is
unchanged on this branch, so the command that ran it, the group it ran in and the runner it ran on are all
the same as on `main`.

**The nondeterminism is measured, not argued.** Same test code, three pushes whose differences are
documentation and shell comments:

| head SHA | run | Java Unit Tests (execution) |
|----------|-----|-----------------------------|
| `64e8d6e0` | 41661043932 | pass |
| `97279dc3` | 41668405877 | **fail** - the assertion above |
| `647ea9f9` | 41669664321 | pass (and the whole CI run green) |

Locally it does not reproduce: five repeated runs of the class at `647ea9f9` on an idle Happy all exited 0
(13.6-13.8 s each), and the class is inside every sharded run reported in section 7 - K=2 at `97279dc3`, K=3
and K=4 at `4fb16ea7`, all `failures+errors=0`, which is the most contended environment this box can give.

**Mechanism, read from the code** (`INFERRED`: consistent with everything above, never reproduced here). The
test snapshots the WireMock request count the moment `pump.stop()` returns
([CoreProgressPumpTest.java:1124-1127](../../agent-control-tower/act-execution/src/test/java/io/aria/conductor/execution/runtime/progress/CoreProgressPumpTest.java#L1124)),
then asserts nothing more reached the wire after `drain()` (line 1131-1133). But `stop()` only guarantees the
worker exited within `DEFAULT_STOP_JOIN_TIMEOUT` = 2 s
([CoreProgressPump.java:119](../../agent-control-tower/act-execution/src/main/java/io/aria/conductor/execution/runtime/progress/CoreProgressPump.java#L119),
join at line 374), and when it does not, it logs the consequence itself: *"a progress fragment may still be
delivered after stop() returned"* (line 379-381). With the test's 20 ms poll interval (line 57) and a 5 s HTTP
timeout (line 70), one round trip that outlasts the join budget leaves the snapshot behind by exactly one
request, which is the `4 vs 5` observed. The assertion states the strong contract without establishing its
own precondition - that the join actually succeeded.

**Why it is not fixed on this branch.** The fix belongs to `act-execution`'s test semantics, and this branch
has deliberately changed no product or test code; folding a test change into a performance PR would also
remove the clean "no `src/` diff" argument that currently proves the failure is not ours. Two candidate
fixes, both of which *tighten* the test rather than relax it, for the owner to choose between:

1. Construct this test's pump with a generous `stopJoinTimeout` (the 9-argument constructor already takes
   one; the slow-sink test at line 242 uses it) so that when `stop()` returns, the worker really has exited
   and the snapshot is meaningful.
2. Let the journal settle before snapshotting - `await().until(() -> requestsToThePumpPath() == previous)`
   across two samples after `stop()` - which tests the intended property (no *new* poll after the halt)
   instead of an instantaneous count.

Neither widens the assertion, and neither is a `@Tag("timing")` candidate: the point of the test is a count,
not a duration. Recorded here rather than silently rerolled until it goes green.
