# Spec — Governed SkillDefinition authoring/approval REST path (Issue #55)
SPEC_ID: c4a793a0-b070-4d78-a6d2-d84206867f15Source issue: HappyLiang12/aria-conductor#55 — "No REST path to author a SkillDefinition; /api/v1/skills is empty on a fresh install"Evidence ledger: `e2e-concurrency-report.md` item **O2**; `act-dashboard/e2e/api/skill-lifecycle.api.spec.ts` A/E.
---
## Problem Statement
On a fresh install the skill registry is empty (`GET /api/v1/skills` → `[]`) and there is **no REST path that creates an assignable `SkillDefinition`**. Concretely:
1. **The only creator of a `SkillDefinition` is not reachable over REST.**   `SelfImprovementService.promoteToSkill` (act-knowledge, Stage 2 → 3 of the self-improvement maturity ladder) is invoked from nowhere in the API layer (`PromptCallController`, `KnowledgeController`, `SkillController` never call it). Even when triggered it is gated by `PromotionEvaluator.evaluateForStage3`, which requires real accumulated usage (an **APPROVED** PROMPT item with ≥ 5 linked uses, plus anti-gaming dominance/rate limits) — i.e. it needs real LLM prompt-call accumulation that cannot happen on a fresh/LLM-less stack.
2. **The only REST "skill" path produces the wrong artifact.**   `POST /api/v1/knowledge/{id}/promote` with `targetType=SKILL` (`KnowledgeController` → `KnowledgeService.promoteKnowledgeItem`) creates only a `KnowledgeItem` of `type=SKILL` (status `PENDING`) plus a `KnowledgeVersion`. It never creates a `SkillDefinition` row. A bare SKILL `KnowledgeItem` is **not assignable**: `AgentService.assignSkill` / `AgentService.setSkills` resolve candidates through `SkillContextProviderImpl.getEnabledSkillsByIds`, which filters on `SkillDefinition` rows where `enabled == true && stage == "SKILL" && template != null`. Therefore `POST /api/v1/agents/{id}/skills` has nothing it can accept.
3. **No governed enable path exists for skills (unlike tools).**   Tools have a governance loop: `ToolApprovalService.submitToolForApproval` creates a `PENDING` TOOL `KnowledgeItem` and stores a **disabled** `ToolDefinition` linked via `knowledgeItemId`; when that item is APPROVED, `ToolApprovalListener`/`ToolApprovalService.onKnowledgeApproved` flips `enabled=true`. Skills have **no equivalent**: nothing ever sets a `SkillDefinition.enabled` to `true` except the ungoverned manual toggle `POST /api/v1/skills/{id}/toggle`. Note `SkillDefinition` rows created by `promoteToSkill` are persisted with `enabled=false` (primitive default) and stay disabled even after their descendant SKILL `KnowledgeItem` is approved.
**Impact.** Operators cannot bootstrap an assignable skill library purely through the API; the author → approve → assign → execute journey cannot be driven end-to-end without LLM self-improvement runs; and the platform's own skill E2E (`skill-lifecycle.api.spec.ts` A/E) documents `/api/v1/skills = []` and skips meaningful coverage because of this gap. `V34__role_defaults_and_skill_templates.sql` explicitly seeds zero skills ("expected, not a defect") and defers to authored skills — but the authoring path does not exist.
---
## Proposed Solution
Deliver a **governed, LLM-free skill authoring + approval path (PENDING → APPROVED) that mirrors tool governance**, so an operator can create an assignable skill over REST on any install. The approving of a `type=SKILL` `KnowledgeItem` becomes the single gate that makes its linked `SkillDefinition` eligible for agent assignment.
### 1. New authoring endpoint — `POST /api/v1/skills`
Add to `SkillController` (`act-knowledge`, base path `/api/v1/skills`, currently GET/list/get/toggle only):
Request body `SkillCreateRequest` (new DTO in `io.aria.conductor.knowledge.dto`):
| Field | Required | Notes ||---|---|---|| `name` | yes (non-blank) | Skill name (display name of the registry entry). || `template` | yes (non-blank) | The executable prompt template (Mustache-style `{{variable}}` placeholders allowed). Must be non-null — assignability and `SkillContext` projection require `template != null`. || `description` | no | `SkillDefinition.description` / `KnowledgeItem.description`. || `triggerConditions` | no | Free-text or JSON object (e.g. `{"variables":["..."]}`); validated as JSON if the body intends JSON — see Error Handling. || `examples` | no | JSON array of example inputs/outputs; validated as JSON if provided. || `tier` | no | Default `TIER_2` (matches `V21` column default). || `sensitivity` | no | Default `INTERNAL`. |
Behavior (single `@Transactional` method `SkillApprovalService.submitSkillForApproval(request)`, new service in `act-knowledge` — structural mirror of `ToolApprovalService`):
1. Create a **PENDING** `KnowledgeItem` of `type=SKILL` whose content is the request `template`, name = request `name`, description = request `description` (fall back to a generated description), `sensitivity`, `currentVersion = v1.0.0`. Persist its `KnowledgeVersion` (`v1.0.0`, content = template) so the existing review flow can resolve a version. Reuse the existing `KnowledgeService.submitKnowledge` (it already writes content through `KnowledgeFileService` and creates the `KnowledgeVersion`) or replicate it in `SkillApprovalService`; do not duplicate storage logic.2. Create and persist a **disabled** `SkillDefinition`:   - `id` = random UUID string, `name`, `description`, `template`, `triggerConditions`, `examples`,   - `knowledgeItemId` = the new `KnowledgeItem.id` (UUID string) — this is the link that the approval listener uses,   - `stage = "SKILL"`, `enabled = false`, `usageCount = 0`, `tier` (default `TIER_2`), `sourcePromptIds = null`.3. Return `201 Created` with `SkillResponse` (see §4) reflecting `enabled=false` and the populated `knowledgeItemId`.
No Flyway migration is required — all `skill_definitions` columns already exist (`V6`, `V21`).
### 2. Approval flips the linked skill to enabled (governance gate)
Add `SkillApprovalService.onKnowledgeApproved(UUID knowledgeItemId)` and a new `SkillApprovalListener` (act-knowledge `listener` package) that handles `KnowledgeApprovedEvent` — an exact structural mirror of `ToolApprovalService` / `ToolApprovalListener`:
- On `@Transactional` handling of `KnowledgeApprovedEvent` whose `type == "SKILL"`: find all `SkillDefinition`s with `knowledgeItemId == event.knowledgeId` (reuse `SkillDefinitionRepository.findByKnowledgeItemId`) and set `enabled = true` (idempotent; only ever transitions `false → true`).- This single listener closes the loop for **both** authoring sources:  - operator-authored skills from §1, and  - pipeline skills created by `SelfImprovementService.promoteToSkill` (whose descendant SKILL item is `PENDING` today; approving it now enables the linked `SkillDefinition`, making the self-improvement path usable end-to-end without changing the evaluator).- Rejection (`decision=REJECTED`) and retirement publish no `KnowledgeApprovedEvent`, so the skill stays / is unaffected — no disable logic in this issue (see Q3).- Guard so non-SKILL approvals never enable skills (a PROMPT/TOOL/etc. item approval must not flip unrelated rows; the `knowledgeItemId` link plus the type check keeps this safe).
### 3. No changes to assignment governance
`AgentService.assignSkill`, `AgentService.setSkills`, `AgentService.getAgentSkills`, `SkillContextProviderImpl` and the runtime `AgentSkillResolver` keep their current gates (assignable only when `enabled && stage == "SKILL" && template != null`). The authored `SkillDefinition` becomes assignable exactly when AC3’s approval flips it. The existing manual `POST /api/v1/skills/{id}/toggle` is preserved as-is (its semantics are pinned by `skill-lifecycle.api.spec.ts` D and `SkillControllerTest`).
### 4. `SkillResponse` additive extension
Extend `SkillResponse` with `template` (and, for round-trip observability, `triggerConditions` and `examples` if already surfaced). Additive-only; existing consumers (`listSkills`, frontend `skills.ts`) are unaffected. This lets `GET /api/v1/skills` / `GET /api/v1/skills/{id}` return what was authored so an operator can confirm content without extra lookups.
### 5. Canonical journey (worked example, no LLM required)
```# 1. Author (disabled until approved)POST /api/v1/skills{ "name": "Summarizer", "description": "3-bullet summarizer",  "template": "Summarize the following in exactly {{count}} bullet points:\n{{text}}" }→ 201 { "id": "s1", "enabled": false, "knowledgeItemId": "ki-1", "stage": "SKILL", ... }
# 2. Approve the linked SKILL knowledge item (governance gate)POST /api/v1/knowledge/ki-1/review  { "decision": "APPROVED", "reason": "ok" }→ 200  (SkillApprovalListener flips s1.enabled = true)
# 3. Assign to an agentPOST /api/v1/agents/{agentId}/skills  { "skillId": "s1" }→ 201  (list now contains s1)
# 4. Runtime injection: resolved SkillContext(s) for the agent include s1's template.```
### 6. Out of scope (unless resolved in Questions)
- No REST trigger for `SelfImprovementService.promoteToSkill`; the self-improvement evaluator (prompt-call accumulation) is unchanged. The governed path from §1 is the LLM-free authoring route this issue asks for.- No usage-count auto-increment, SCRIPT/WORKFLOW progression, or frontend wiring in this issue.

## Acceptance Criteria
Unit/integration tests must be added under `act-knowledge` (plus optionally an API E2E step); verification command `cd agent-control-tower && mvn test -pl act-common -pl act-knowledge`, full suite `mvn clean test -Dspring.profiles.active=h2`.
- **AC1 — Authoring creates the full artifact pair.** `POST /api/v1/skills` with a valid body returns `201` and, in a single transaction, persists (a) a `KnowledgeItem` of `type=SKILL` with `status=PENDING` and `currentVersion=v1.0.0`, plus its `KnowledgeVersion`, and (b) a `SkillDefinition` with `stage=SKILL`, `enabled=false`, `template` = request template, `usageCount=0`, and `knowledgeItemId` equal to the new item id. `GET /api/v1/skills/{id}` and `GET /api/v1/skills` surface the skill (including `template`).- **AC2 — Not assignable before approval.** Before the linked item is approved, `POST /api/v1/agents/{agentId}/skills` with the authored skill id returns `409` and does not create an `agent_skills` row (existing governance message).- **AC3 — Approval enables the linked skill.** Approving the linked `PENDING` SKILL item via `POST /api/v1/knowledge/{kiId}/review {decision:APPROVED}` returns `200`, and exactly the `SkillDefinition`(s) whose `knowledgeItemId == kiId` are flipped to `enabled=true`. Re-listening/duplicate events are idempotent (no error, stays `true`).- **AC4 — Assignable after approval, end-to-end.** After AC3, `GET /api/v1/skills?enabled=true` includes the skill; `POST /api/v1/agents/{agentId}/skills` returns `201`; `GET /api/v1/agents/{agentId}/skills` returns a `SkillContext` carrying the authored `template`; agent creation/list responses (name-based `skills[]`) include it. No regression in disabled/unlinked filtering.- **AC5 — Reject leaves disabled; unrelated approvals are inert.** `REJECTED` review leaves `enabled=false`; approving a non-SKILL item (e.g. PROMPT/GUIDELINE) or an item with no linked `SkillDefinition` changes nothing (no-op, no exception); unknown knowledge id in the listener is a no-op.- **AC6 — Fresh-install bootstrap via REST only.** On an empty database (no LLM, no prompt calls), the sequence author → approve → assign → agent skill context resolves (AC1–AC4) succeeds purely through the public API.- **AC7 — Validation.** Blank/missing `name` or `template` → `400`; unparseable JSON in `triggerConditions`/`examples` → `400`; duplicate authored skill `name` → `409`; review of an already-decided (non-`PENDING`) item still → `409` (`InvalidStateTransitionException`); unknown agent on assignment still → `404`.- **AC8 — Self-improvement path converges.** Approving a `type=SKILL` `KnowledgeItem` produced by `SelfImprovementService.promoteToSkill` also enables its linked `SkillDefinition` via the same listener (existing `SelfImprovementServiceTest`, `SkillPromotionIntegrationTest`, `PromotionEvaluatorTest` remain green; evaluator thresholds/anti-gaming unchanged).- **AC9 — New tests exist.** Add `SkillApprovalServiceTest` (create links+disables; approve enables only linked SKILL; unknown id no-op; empty repo no-op; reject does not enable), `SkillApprovalListenerTest` (type guard, forwards to service), `SkillController` create tests (`201`, `400` validation, `409` duplicate), and an integration test covering AC1→AC4 in one flow. Mirror the existing tool-governance test style.- **AC10 — No regressions.** Tool governance tests (`ToolApprovalServiceTest`, `ToolApprovalListenerTest`), `AgentServiceTest`/`AgentControllerTest` skill/tool assignment gates, `SkillControllerTest` read/toggle behavior, and `SkillContextProviderImplTest` continue to pass. No migration file added in this change (unless a reviewer mandates a uniqueness constraint — see Q3/Q4).

## Error Handling
Reuse the existing global + controller exception contract (`GlobalExceptionHandler` in `act-common`, `KnowledgeController` local handlers); do not introduce new status semantics.
| Case | Status | Mechanism ||---|---|---|| Bean-validation failure (`name`/`template` blank, bad enum) | `400` | `MethodArgumentNotValidException` → `GlobalExceptionHandler`; message = `field: message`. || Malformed request body (unreadable JSON, wrong types) | `400` | `HttpMessageNotReadableException` → `GlobalExceptionHandler`. || Invalid `triggerConditions`/`examples` (invalid JSON when a JSON payload is expected) | `400` | Service-level `IllegalArgumentException` → `GlobalExceptionHandler`. || Duplicate authored skill `name` | `409` | Service-level duplicate check throwing `IllegalStateException` (or `InvalidStateTransitionException`) → `GlobalExceptionHandler` maps to `CONFLICT`. Best-effort service check only; no schema unique-constraint change (protects the self-improvement path which may legitimately reuse derived names). || Review of a non-`PENDING` knowledge item | `409` | Existing `InvalidStateTransitionException` (unchanged). || Assigning an unknown/non-enabled/disabled skill | `409` | Existing `AgentService.assignSkill`/`setSkills` `IllegalStateException` (unchanged). || Unknown agent on assignment / unknown skill id on read | `404` | `ResourceNotFoundException` / controller `notFound()`. || Unknown knowledge id in the approval listener | no-op (no error) | `onKnowledgeApproved` finds zero linked rows and returns silently. || Persistence / unexpected failures | `500` | `DataIntegrityViolationException`, `PersistenceException`, catch-all in `GlobalExceptionHandler`. || Transactional integrity during authoring | rollback | `submitSkillForApproval` is one `@Transactional` write; a failure in the `KnowledgeItem`+`KnowledgeVersion`+`SkillDefinition` writes rolls back all three — no orphaned rows. || Concurrency | safe / idempotent | The review path is already serialized by the atomic conditional-update fix (F1 in the ledger). The approval listener only ever sets `enabled=true` (idempotent) and performs no read-then-write toggle. Duplicate-name check is best-effort and documented as not a hard guarantee under racing creates. |
Notes:- No authentication is added; the trust boundary is unchanged from the rest of the API (`SECURITY.md`).- The pre-existing manual `POST /api/v1/skills/{id}/toggle` remains a deliberate, ungoverned escape hatch (pinned by existing tests); it is not part of the new governance contract.

## Questions
- Q1 — Authoring scope: should this issue deliver **only** the governed operator authoring path (§1–§4, recommended), or must it **also** expose a REST trigger for `SelfImprovementService.promoteToSkill` (Stage 2→3), accepting that it will fail the evaluator until real prompt-call usage accumulates?- Q2 — Approval gating: must a skill be assignable **only after** its linked SKILL `KnowledgeItem` is APPROVED (strict tool-governance parity, recommended), or should `POST /api/v1/skills` optionally accept an "enable immediately / skip review" flag for single-operator/local and CI use?- Q3 — Post-approval content lifecycle: if an approved skill's linked `KnowledgeItem` is later edited (`updateKnowledge` → new `PENDING` version, then re-approved) or retired, should the implementation (a) keep `SkillDefinition.template` immutable and leave `enabled` untouched in this issue (recommended), (b) re-sync `template` from the newly approved version on each approval, or (c) also auto-disable the skill when its item is retired/edited?- Q4 — Name uniqueness: should duplicate authored skill names be rejected at authoring time (service-level, recommended), or should a database-level unique constraint/index be added to `skill_definitions.name` (requires a new Flyway migration and must not break derived pipeline names)?
