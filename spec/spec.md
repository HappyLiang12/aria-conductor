# Spec: review_knowledge requires UUID but Aria has no name-to-UUID lookup tool
**Issue:** #38 — `review_knowledge requires UUID but Aria has no name-to-UUID lookup tool`**Labels:** `bug`**Branch:** main @ d65f916 (h2 profile)
---
## Problem Statement
Aria's `review_knowledge` tool requires its `id` parameter to be a UUID, but Aria has no way to resolve a knowledge item's **name** to its UUID. The knowledge tools Aria exposes (via `KnowledgeToolHandler` in `act-aria`) only accept `id` (UUID) on the review/retire paths, and no `find_knowledge` / `get_knowledge_by_name` tool exists anywhere in the Aria tool surface.
When Aria stores a knowledge item (e.g. `store_knowledge(name='project-architecture-basics', ...)`), the tool response reports the new UUID, but a multi-step agentic flow does not reliably thread that UUID forward. When Aria then tries to approve its own freshly-created item with `review_knowledge(id='project-architecture-basics', decision='APPROVED')`, `UUID.fromString(id)` throws `IllegalArgumentException`, which the handler's outer `catch` maps to `Error: Invalid UUID string`.
Current behavior in `KnowledgeToolHandler` (`agent-control-tower/act-aria/src/main/java/io/aria/conductor/aria/tools/handlers/KnowledgeToolHandler.java`):- `reviewKnowledge(...)` (line 148) and `retireKnowledge(...)` (line 170) both call `UUID.fromString(id)` directly and fail on any non-UUID input.- `search_knowledge` / `list_knowledge` return names but **not** the item's UUID, so Aria cannot derive the ID from a listing.
### Impact- Aria cannot approve/reject knowledge items it created.- Knowledge items stay `PENDING` forever and are never promoted to `APPROVED`.- The knowledge lifecycle (`PENDING → APPROVED → usable`) is effectively blocked for agent-created items.- This violates the intended self-contained workflow where Aria stores, reviews, and later queries its own knowledge.
---
## Proposed Solution
Adopt the **id-or-name resolution** convention already established in this codebase by `AgentToolHandler.resolveAgentId` (try UUID first, else resolve by name) and **complement it with an explicit `find_knowledge` lookup tool**. The issue offers these as alternative ("Either…OR…") options; this spec recommends implementing both because they are complementary and low-cost, and defers the final scope to the **Questions** section.
### 1. id-or-name resolution in `review_knowledge` and `retire_knowledge`
Modify `KnowledgeToolHandler` (`agent-control-tower/act-aria/src/main/java/io/aria/conductor/aria/tools/handlers/KnowledgeToolHandler.java`):
- Add a private resolution helper mirroring `AgentToolHandler.resolveAgentId`:  1. If `id` is blank → return null (caller emits existing "Missing required parameter: id").  2. Try `UUID.fromString(id.trim())`; on success use that UUID directly.  3. Otherwise treat the value as a **name** and look it up in `KnowledgeItemRepository`.  4. No match → return a "not found" marker; the caller emits `Error: Knowledge not found: <value>`.  5. Multiple items share the exact name → return an ambiguity marker; the caller emits an error listing the candidate items (id, type, status) and asks the caller to retry with the UUID (see Questions Q2).- `reviewKnowledge(...)`: resolve `id` via the helper, then call `knowledgeService.reviewKnowledge(uuid, request)` as today.- `retireKnowledge(...)`: resolve `id` via the helper, then call `knowledgeService.retireKnowledge(uuid)` as today.
**Repository changes** (`agent-control-tower/act-knowledge/src/main/java/io/aria/conductor/knowledge/repository/KnowledgeItemRepository.java`):- Add `List<KnowledgeItem> findByName(String name)` (names are NOT unique — see V1 `knowledge_items` DDL, no unique constraint on `name`), so the handler can detect both the single-match and multi-match cases. (`findByNameAndType` exists but requires a type the caller may not know; name-only lookup is required here.)
**No DB migration needed for review/retire**: the seeded `tool_definitions.parameters` JSON for `review_knowledge` and `retire_knowledge` already types `id` as `"type":"string"` (V22), so the schema already permits non-UUID values; only runtime behavior changes.
### 2. New `find_knowledge` lookup tool (name → id/status)
Add a `find_knowledge` tool that resolves a knowledge item name to its identity, giving Aria (and operators) an explicit, reliable way to obtain the UUID:
- **Handler:** add `case "find_knowledge" -> findKnowledge(arguments);` in `KnowledgeToolHandler.execute(...)`.- **Behavior:** `find_knowledge(name='<name>')` returns the matching item(s) as `Name | ID | Type | Status` lines, reusing the existing `KnowledgeItemRepository.findByName` lookup. Missing name → `Error: Missing required parameter: name`. No match → `Error: Knowledge not found: <name>`. Multiple matches → list all matching items (id, type, status) so the caller can pick the UUID.- **Tool registry seeding:** add a Flyway migration (next version number, e.g. `V39__seed_find_knowledge_tool.sql`) following the existing `V25__seed_additional_tools_and_fixes.sql` / `V38__seed_workflow_tools.sql` pattern:  - insert a knowledge item row `'Seed tool: find_knowledge'` (TOOL, APPROVED, INTERNAL) with a deterministic UUID,  - insert a `tool_definitions` row (`handler_class='knowledgeToolHandler'`, `tier='TIER_2'`, `category='PLATFORM'`, `parameters='{"type":"object","properties":{"name":{"type":"string"}},"required":["name"]}'`, `enabled=TRUE`),  - grant it to the `ARIA` role via `role_tool_templates` (mirroring the ARIA-grants in V22).- **Test seed parity:** update `act-app/src/test/resources/tool-registry-seed.sql` and any registry assertions (`ToolRegistrySeedTest`, `RoleDefaultsIntegrationTest`) so tests reflect the new tool.
### 3. Prompt / tool-description updates
Update the Aria system-prompt tool descriptions so the LLM knows a name is accepted:
- `agent-control-tower/act-aria/src/main/java/io/aria/conductor/aria/init/AriaDefaultAgentInitializer.java`:  - `review_knowledge` description (line ~68): change "requires id, decision, optional reason" to "requires id (UUID or item name) or name, decision, optional reason".  - Add `find_knowledge` to the standard-tool list (lines ~153-154): `find_knowledge: Look up a knowledge item's ID and status by exact name (requires name)`.- `agent-control-tower/act-aria/src/main/java/io/aria/conductor/aria/service/AriaService.java` (line ~225): apply the same description edits to the mirrored prompt text.
### 4. Out of scope (unless reviewers decide otherwise — see Questions Q3)
- `packages/mcp-server` `review_knowledge` (different surface: REST-based, `approved` boolean param, `id: uuid` zod schema) is **not** part of this fix unless explicitly requested.- REST API `POST /api/v1/knowledge/:id/review` in `act-knowledge` is unchanged; it remains UUID-only at the HTTP layer.

## Acceptance Criteria
1. **Aria can review by name.** After `store_knowledge(name='project-architecture-basics', content=..., type=...)` produces a `PENDING` item, `review_knowledge(id='project-architecture-basics', decision='APPROVED')` succeeds, transitions the item to `APPROVED`, and publishes `KnowledgeApprovedEvent`. The tool response no longer contains `Error: Invalid UUID string`.2. **UUID input is unchanged.** `review_knowledge(id=<valid-uuid>, decision=...)` and `retire_knowledge(id=<valid-uuid>)` behave exactly as before (same messages, same service calls, same status transitions). Existing tests in `KnowledgeToolHandlerTest` and `KnowledgeToolHandlerEdgeCasesTest` continue to pass unmodified.3. **`retire_knowledge` accepts id-or-name.** `retire_knowledge(id='<name>')` on an `APPROVED` item retires it and reports `Status: RETIRED`.4. **New `find_knowledge` tool exists and works.** `find_knowledge(name='project-architecture-basics')` returns the item's `ID`, `Type`, and `Status`; Aria can take the returned UUID and pass it to any UUID-based tool.5. **Tool registry + role wiring.** `find_knowledge` is present in `tool_definitions`, seeded by a Flyway migration, and granted to the `ARIA` role (via `role_tool_templates`). It appears in `ToolRegistrySeedTest` / `RoleDefaultsIntegrationTest` expectations and the `act-app` test seed SQL.6. **Prompt text updated.** Both `AriaDefaultAgentInitializer` and `AriaService` document that `review_knowledge` (and `retire_knowledge`) accept a name, and list `find_knowledge`.7. **Error paths are user-friendly** (see Error Handling): no raw `Invalid UUID string` leaks; unknown names, ambiguous names, and missing params produce actionable messages.8. **Tests.** Unit tests added in `KnowledgeToolHandlerTest` / `KnowledgeToolHandlerEdgeCasesTest` (and a repository slice test for `findByName` if added) covering: name resolution success, unknown name, multiple matches, invalid-UUID-as-name handling, and `find_knowledge` success/not-found/multiple-match. `KnowledgeItemRepositorySliceIntegrationTest` covers `findByName` multi-match semantics.9. **Validation commands pass:**   - `cd agent-control-tower && mvn test -pl act-aria`   - `cd agent-control-tower && mvn test -pl act-knowledge`   - `cd agent-control-tower && mvn test -pl act-app` (Flyway migration + tool-registry seed tests)

## Error Handling
| Scenario | Behavior ||---|---|| `id` missing / blank on `review_knowledge` / `retire_knowledge` | Existing message: `Error: Missing required parameter: id` (unchanged). || `decision` missing or invalid on `review_knowledge` | Existing message: `Error: Missing required parameter: decision` / `Error: Invalid decision: <value>. Valid: APPROVED, REJECTED` (unchanged). || Value is a valid UUID | Resolved and used as today; no error. || Value is not a UUID and no item has that name | `Error: Knowledge not found: <value>` (replaces the current raw `Error: Invalid UUID string: <value>`). || Value is not a UUID and multiple items share that exact name | `Error: Multiple knowledge items found with name '<name>'. Specify the UUID: <name> | <id1> | <type1> | <status1>, ...` (candidate list). || `find_knowledge` with missing/blank `name` | `Error: Missing required parameter: name`. || `find_knowledge` with no match | `Error: Knowledge not found: <name>`. || `find_knowledge` with multiple matches | Returns all matches as a list (`Name | ID | Type | Status`) rather than erroring, since listing is the tool's purpose. || Service-level failure (e.g. item not `PENDING` on review, `InvalidStateTransitionException`, not-found from service) | Existing outer `try/catch` in `execute(...)` maps to `Error: <message>` (unchanged). || `find_knowledge` invoked as `review_knowledge`'s name parameter containing characters that look like an invalid UUID | Treated purely as a name; never surfaced as a UUID parse error. |
Note on concurrency: name resolution reads use the existing repository queries; the review state machine's pessimistic-write lock (`findByIdForUpdate`) is preserved because resolution produces a UUID that is then passed to the existing `reviewKnowledge(UUID, ...)` service path. No new locking semantics are introduced.

## Questions
- Q1. Which resolution mechanism should be shipped? (a) id-or-name acceptance in `review_knowledge`/`retire_knowledge` only [minimal], (b) `find_knowledge` lookup tool only [explicit two-step flow], or (c) both [recommended — names unblock the immediate repro and the lookup tool gives a durable name→UUID path for other tools].- Q2. `knowledge_items.name` is not unique (no DB constraint). When a name resolves to multiple items, should the tool (a) fail with an error listing the candidates and require the UUID [recommended — deterministic, prevents acting on the wrong item], or (b) resolve to the first match (e.g. earliest `created_at`)?- Q3. Should the fix also extend to the `packages/mcp-server` `review_knowledge` tool (REST-backed, `approved` boolean, `id` constrained to `z.string().uuid()`)? Recommended: out of scope for this issue; the issue and repro concern Aria's `act-aria` tools.
