# Spec: Add authentication/authorization to the REST API
**Source issue:** #1 (`[security] Add authentication/authorization to the REST API`) — labels: `security`, `priority:P1`**Repo:** HappyLiang12/aria-conductor**Version target:** v0.2 hardening item (see `SECURITY.md`)
---
## Problem Statement
Every REST endpoint in Aria Conductor is currently unauthenticated. Anything bound to`/api/v1/**` — agents, workflows, runs, tools/skills, LLM providers, system config,harness profiles, dashboard/kanban/DoD/approvals/knowledge/reports/notifications, theAria chat (including the SSE streaming variant `/api/v1/aria/chat/stream`), and the`h2`-profile dev SQL runner (`/api/v1/dev/sql/**`) — can be invoked by any client thatcan reach the backend port (`8080`), with no credential check. Concretely anunauthenticated caller can:
- read and mutate **LLM provider records including their stored API keys** (`/api/v1/llm-providers`),- create agents and start/retry runs, **consuming paid LLM budget** and triggering  sandboxed execution,- mutate governance state (approve/reject approvals, transition kanban/DoD items, edit  workflow chains, manage knowledge items),- on the `h2` dev profile, execute arbitrary SQL against the app database  (`/api/v1/dev/sql`), and- read operational data (audit events, notifications, run trajectory, agent  configurations).
`SECURITY.md` documents this as a known limitation: **"No built-inauthentication/authorization. All `/api/v1/**` endpoints are currentlyunauthenticated."** The guidance for non-local use is to place the service behind anexternal authenticating gateway/reverse proxy. That is an operational burden and isinconsistent: nothing enforces it, so a default or misconfigured deployment can beexposed to untrusted networks with no protection; the documented fallback for Dockerbinds only to `127.0.0.1` by default.
The issue asks for **built-in** auth (one of: API key / Bearer token / session) sonon-local deployments no longer depend solely on an external gateway, and requires theCI smoke test to be updated to send credentials once auth lands. `priority:P1`.
### Non-goals (out of scope for this item)
- Encryption of LLM provider keys at rest (tracked separately in #3; see `SECURITY.md`).- Full user-management / multi-tenant identity-provider integration.- Auth between the backend and its own internal runtimes (LangChain ADK, OpenSandbox),  which are separate network endpoints; only the HTTP API surface of `act-app` is in scope.- Per-route role-based access control beyond a single operator credential (see Questions).
---
## Proposed Solution
Add **built-in, deployment-level HTTP authentication** to the `act-app` REST API using a**static shared API key accepted as an `Authorization: Bearer <key>` header**, configuredfrom the environment. The key is a single "operator" secret for the whole deployment,chosen by the operator; no user accounts, sessions, or database persistence areintroduced for v0.2. This is the smallest change that removes the documented"no built-in auth" gap, is trivially compatible with an external gateway (it can forwardcredentials), and requires no new tables or migrations.
### Configuration
- New environment variable **`ARIA_API_KEY`**, relaxed-bound to a new config property  (e.g. `aria.api-key`, or `app.auth.api-key`) following the existing relaxed-binding  pattern in `application.yml`, e.g. `opencode.sandbox-api-key: ${OPENSANDBOX_API_KEY:}`.- **Enforcement is enabled iff a non-blank `ARIA_API_KEY` is configured.**  - Configured → all protected paths require a valid Bearer token.  - Unset/blank → current behaviour is preserved (permissive) so local dev, the existing    test suite, and the frontend Playwright E2E jobs that do not set the key keep    working; the app must log a prominent startup WARN (e.g.    `AUTH DISABLED: ARIA_API_KEY not set. All /api/v1/** endpoints are open. Do not expose this deployment publicly.`).- The presented token must be compared with the configured key in **constant time**  (e.g. `MessageDigest.isEqual`); never log the key itself or full `Authorization`  header values.
### Enforcement scope
Protected (require a valid Bearer token when auth is enabled):
- `/api/v1/**` — all existing and future endpoints under the API prefix, including SSE  (`POST /api/v1/aria/chat/stream`) and the dev SQL runner (`/api/v1/dev/sql/**`).- `/actuator/**` **except** `/actuator/health` (kept open so container healthchecks in  `docker-compose.yml` and the CI `start-stack` readiness probe keep working).
Exempt (never require the token):
- `/actuator/health` (liveness/readiness probe used by compose + CI).- `OPTIONS` preflight requests (CORS) — must pass through unauthenticated.- SpringDoc/OpenAPI paths if exposed (`/v3/api-docs`, `/swagger-ui/**`) — see Questions.- `/h2-console/**` — already restricted to the `h2` dev profile; leave as-is (see Questions).
### Mechanism (recommended)
Prefer a **lightweight authentication filter** (a `OncePerRequestFilter` / servlet`Filter` registered in `act-app`, or in `act-common` if reuse is desired) over pulling in`spring-boot-starter-security` for v0.2. Rationale: the reactor currently has **no**Spring Security dependency, and adding the starter flips on a large set of defaultbehaviours (auto-generated basic-auth user, CSRF, security headers, session handling)that would ripple through dozens of existing controller/integration tests and the`/actuator` defaults. A single filter:
- runs before request dispatch so unauthenticated calls are rejected before any  controller/`@RestControllerAdvice` handling,- short-circuits when auth is disabled (key blank) to preserve current behaviour,- parses `Authorization: Bearer <token>`, rejects other/malformed schemes with `401`,- accepts the request when the presented token matches the configured key (constant-time  comparison),- otherwise writes a JSON error body consistent with the existing  `GlobalExceptionHandler` response schema (see Error Handling) and sets  `WWW-Authenticate: Bearer realm="aria-conductor"`,- skips the exempt paths above.
If the team instead chooses full Spring Security (see Questions), the same pathallow-list, property, and `401` semantics above remain the contract.
### Frontend dashboard
The React dashboard (`act-dashboard`) must keep working when auth is enabled:
- Add operator-configurable token entry (persisted in `sessionStorage`, never  `localStorage` by default — see Questions) and attach it as  `Authorization: Bearer <token>` in the axios `client.ts` request interceptor  (it currently only attaches `X-Correlation-ID` and logs a `console.warn` on `401`).- When a request returns `401`, surface a lightweight "set API token" prompt rather than  the current `console.warn`; after the operator enters a token, retry transparently.- Vite dev/preview proxy config needs no change (it forwards `/api` and `/ws` headers  as-is; the `Authorization` header must be forwarded — verify the proxy does not strip it).- WebSocket (`/ws`, used by the real-time dashboard): the browser WebSocket API cannot set  the `Authorization` header, so if `/ws` is in scope the handshake must accept the token  via a query parameter (e.g. `?token=`) or a `Sec-WebSocket-Protocol` subprotocol — see  Questions. If `/ws` is deferred, document that it remains unauthenticated.
### CI smoke test update
Update the `e2e-smoke` job in `.github/workflows/ci.yml` (and the `start-stack` actiononly if needed) so that once auth is exercised:
- the backend is started **with `ARIA_API_KEY` set** (a throwaway value generated in the  job is fine),- every `/api/v1/**` smoke `curl` sends `-H "Authorization: Bearer ${ARIA_API_KEY}"`  (agent list, dashboard summary, workflows, knowledge, and any other covered endpoints),- `/actuator/health` remains checked **without** credentials,- add a **negative assertion**: an unauthenticated request to `/api/v1/agents` must fail  with HTTP `401` while auth is enabled, so a regression to open endpoints is caught.
The `java-integration-tests` lane must keep a dedicated test that boots with the keyconfigured (e.g. via `@DynamicPropertySource`/`@TestPropertySource`) to assert the `401`and `200` paths; all other existing integration/controller tests keep running in thedefault permissive mode and must stay green. Frontend Playwright E2E jobs run in thedefault (unset-key) mode and stay green.
### Documentation
- `SECURITY.md`: remove/mark-resolved the "No built-in authentication" limitation;  document `ARIA_API_KEY`, enforcement scope, the default-open behaviour when unset, and  the recommendation to still front non-local deployments with a gateway/TLS.- `.env.example`: add commented `ARIA_API_KEY=` entry with guidance.- `README.md`: note auth opt-in and add the header to the `curl` examples (LLM provider  creation, agent provider switch) or note  "append `-H 'Authorization: Bearer $ARIA_API_KEY'`".

## Acceptance Criteria
1. **Config gating.** When `ARIA_API_KEY` is unset/blank the application boots with   today's behaviour: every `/api/v1/**` call succeeds without credentials, a startup   WARN log records that auth is disabled, and all pre-existing unit/integration/controller   tests pass unchanged.2. **Enforcement.** When `ARIA_API_KEY=<key>` is set, a request to any `/api/v1/**`   endpoint (e.g. `GET /api/v1/agents`, `GET /api/v1/dashboard/summary`,   `GET /api/v1/workflows`, `GET /api/v1/knowledge?type=WORKFLOW`,   `POST /api/v1/aria/chat/stream`, `POST /api/v1/dev/sql/execute` on the `h2` profile)   returns `401` when no `Authorization` header is present.3. **Valid token.** The same requests succeed (`200`/expected status) with header   `Authorization: Bearer <key>`.4. **Invalid token.** A wrong, empty, or non-`Bearer` token returns `401` with a JSON   body matching the `GlobalExceptionHandler` schema (`timestamp`/`status`/`error`/`message`)   and a `WWW-Authenticate` header; the request never reaches the controller/service layer.5. **Health check exempt.** `GET /actuator/health` returns `200` with or without a token   while auth is enabled.6. **Constant-time comparison.** Token validation uses a constant-time comparison; the   key and full `Authorization` header are never written to logs, error bodies, or trace   output (verified by an assertion in the auth unit tests).7. **Frontend.** With auth enabled, the dashboard prompts for a token on `401`, attaches   `Authorization: Bearer` to subsequent API calls, and all dashboard pages that worked   pre-auth still work once the operator supplies the token.8. **CI.** `e2e-smoke` starts the backend with `ARIA_API_KEY`, sends the Bearer header on   every `/api/v1` check, keeps the unauthenticated `/actuator/health` probe, and adds a   negative `401` assertion; the job is green. Frontend Playwright E2E jobs run in the   default (unset-key) mode and remain green.9. **Tests.** New unit tests cover: enabled/disabled behaviour, the path allow-list,   malformed/missing/wrong-token `401`s, constant-time compare, and exempt   `OPTIONS`/health; at least one Spring integration test boots with the key set and   asserts both the `401` and authenticated `200` paths end-to-end.10. **Docs.** `SECURITY.md`, `.env.example`, and `README.md` are updated as described    under Documentation; no secrets are added to the repo.

## Error Handling
- **Missing/invalid/wrong-scheme credentials → HTTP 401 Unauthorized.** The auth filter  (which runs before controllers) returns a JSON body shaped like existing error  responses so clients get a consistent contract:  `{ "timestamp": "<ISO-8601>", "status": 401, "error": "Unauthorized", "message": "<message>" }`,  plus `WWW-Authenticate: Bearer realm="aria-conductor"`. The `message` is deliberately  generic (e.g. "Invalid or missing API key") and does **not** distinguish "no token",  "bad token", or "malformed header", to avoid leaking which credentials are valid.  Missing vs. malformed header both map to `401` (not `400`) for the same reason.- **Unauthenticated access to a non-existent protected path → 401, not 404.** Because the  filter runs before dispatch, unknown routes under a protected prefix must not reveal  their existence to unauthenticated callers. (Today unknown paths yield `404` via  `NoResourceFoundException` in `GlobalExceptionHandler`; the filter changes precedence  for protected prefixes only.)- **CORS preflight (`OPTIONS`) → always pass through.** Must not be rejected by the auth  filter. The existing CORS mapping allows all headers (`allowedHeaders("*")`) so the  `Authorization` header is permitted; keep `allowCredentials(false)` since Bearer tokens  do not rely on cookies.- **No credential echo / no log leakage.** Auth failures are logged at debug/warn with the  correlation ID (`X-Correlation-ID`, already attached by the dashboard) but never include  the presented token, the configured key, or full header values.- **Disabled mode (key unset).** Not an error condition; it is the documented permissive  local/dev default and must log the one-time startup warning. When `ARIA_API_KEY` is set  there is no "degraded" path: enforcement is strict. Whether non-dev deployments must  fail closed instead is a deployment-policy decision (see Questions).- **Downstream errors during authenticated requests** continue to be handled by the  existing `GlobalExceptionHandler` (`400/404/409/429/500`, etc.); auth handling does not  swallow or alter them.- **Rate limiting / brute-force throttling on the auth path** is explicitly out of scope  for v0.2 (single static key; note it in `SECURITY.md` as a future item).

## Questions
- Auth mechanism for v0.2: is the recommended lightweight static shared Bearer API key (`ARIA_API_KEY`) acceptable, or must this ship with full Spring Security and a real user/session/role model now, or is "external gateway only" the intended direction?- When `ARIA_API_KEY` is not configured, should the default stay open (recommended, keeps local dev + existing tests + frontend E2E working) or fail closed on non-dev profiles?- Should v0.2 support only a single shared key, or multiple keys / a rotation mechanism / per-role keys (e.g. read-only vs admin)?- Is the real-time WebSocket (`/ws`) handshake in scope for auth (token via query param or subprotocol), or is it deferred and documented as unauthenticated?- Frontend token UX: operator-entered token prompted on `401` and kept in `sessionStorage` (recommended), a dedicated login page, or the token injected at build/deploy time via environment (no UI)?- Should auth also cover the SpringDoc/OpenAPI surface (`/v3/api-docs`, `/swagger-ui/**`) and the dev-only `/h2-console`, or is protecting `/api/v1/**` plus non-health actuator endpoints sufficient for this item?
