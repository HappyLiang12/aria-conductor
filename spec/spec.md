# Spec — [security] Add authentication/authorization to the REST API
Source: Issue #1 (HappyLiang12/aria-conductor), label `security`, `priority:P1`.Issue body: *"All `/api/v1/**` endpoints are currently unauthenticated. For anynon-local deployment the service must sit behind an authenticating gateway, orgain built-in auth (API key / Bearer / session). Update the CI smoke test to sendcredentials once auth lands. v0.2 hardening item; see SECURITY.md."*
## Problem Statement
Every endpoint under `/api/v1/**` in the Aria Conductor backend is currentlyunauthenticated. This is an explicit, documented trade-off for local evaluation(SECURITY.md → *Known Limitations*), but it means **any** process that can reachthe service on a non-local network can:
- read, create, modify, and delete agents, tools, skills, workflows, and runs;- read and write knowledge items and review/promote knowledge;- manage LLM provider credentials (including API keys stored in the DB);- trigger and approve/cancel agent runs and change governance/approval state;- mutate system configuration and issue arbitrary tool/shell invocations via the  agent execution path.
Because there is no identity or trust boundary today, a single exposed deploymentcompromises the entire control plane, including the credentials of every LLMprovider configured in it. The v0.2 hardening goal (SECURITY.md) requires that anon-local deployment cannot be brought up with an open API, and that the CI smoketest verifies the new credential requirement rather than the current "no auth"behavior (`.github/workflows/ci.yml`, `e2e-smoke` job curls`/api/v1/agents`, `/api/v1/dashboard/summary`, `/api/v1/workflows`,`/api/v1/knowledge` with no credentials).
A secondary gap: agents that run inside the sandbox and talk back to the API(e.g. SDD/dev agents using `gh`/`curl` against the control plane) currently haveno way to authenticate either, because no credential material is provisioned.
## Proposed Solution
Add a **built-in authentication layer** to the backend in front of all`/api/v1/**` routes, together with configuration, a small credential-provisioningpath, docs, and updated CI smoke coverage. The default must remain zero-frictionfor local development while being locked-down for non-local deployments.
The recommended mechanism (subject to the **Questions** section) is a lightweight**shared-secret API key presented as a `Bearer` token or `X-API-Key` header**,implemented as a servlet filter / `OncePerRequestFilter` registered before thecontrollers. This is intentionally stateless (no session store, no user table)and matches the current single-operator, single-node deployment model. A fullusername/password session + login UI is explicitly out of scope unless themaintainers choose otherwise (see Questions Q1).
Concretely:
1. **Auth filter + matcher**   - Add a `SecurityFilterChain`/`OncePerRequestFilter` (in `act-app`, applied     app-wide) that protects all `/api/v1/**`.   - Permit unauthenticated, with no `WWW-Authenticate` requirement: only the     health/info actuator endpoints (`/actuator/health`, `/actuator/info`) and     non-`/api/v1` static/error surfaces. Everything under `/api/v1/**` requires     a valid credential.   - H2/dev-only surfaces remain gated to the `h2` profile as today.
2. **Configuration (env-driven, no secrets in code)**   - New property `app.security.enabled` (env `APP_SECURITY_ENABLED`).   - New property `app.security.api-keys` (env `AUTH_API_KEYS`) — a comma/space     separated list of keys, or of hex SHA-256 hashes (prefix entries with     `sha256:`). Storing only hashes at rest is preferred; plaintext env is     accepted for operability but never logged.   - Defaults:     - `mariadb` (production) profile → `app.security.enabled=true` and startup       **fails fast** if no key is configured (see Error Handling).     - default/h2 (local dev) profile → `app.security.enabled=false` unless       explicitly overridden, preserving today's local UX.
3. **Credential check**   - Accept the key from `Authorization: Bearer <key>` or `X-API-Key: <key>`.   - Compare in constant time against the configured set (hash comparison when     hashes are configured).   - On success, set a lightweight request attribute/principal (e.g.     `authenticated` + key id/hint) for audit logging; do not invent user roles.
4. **Provisioning to agents / sandboxes**   - Expose the generated key to agent sandboxes via the existing     `opencode.sandbox-env` mechanism (e.g. `ARIA_API_KEY`/`GH_TOKEN`-style env)     so sandboxed agents can call the API authenticated. If no key is configured     (local dev, auth disabled), the variable is simply not injected.
5. **Docs**   - Update SECURITY.md *Known Limitations* to remove the "no built-in auth"     bullet and document configuration, the recommended gateway note, and key     rotation.
6. **CI smoke test**   - In `.github/workflows/ci.yml` `e2e-smoke`, configure a test key for the     stack and add `Authorization: Bearer <test-key>` to the existing curls     (`/api/v1/agents`, `/api/v1/dashboard/summary`, `/api/v1/workflows`,     `/api/v1/knowledge`).   - Add a negative check: calling `/api/v1/agents` **without** credentials must     return `401` (proving auth is actually enforced), and with a wrong key must     return `401`/`403`.
## Acceptance Criteria
- **AC1 — Enforcement:** With `app.security.enabled=true`, every  `/api/v1/**` request without a valid credential returns `401 Unauthorized`  (and no handler logic runs). Verified by an automated test (mock MVC + a live  boot test) covering a representative sample of controllers: `/agents`,  `/workflows`, `/runs`, `/tools`, `/skills`, `/knowledge`,  `/llm-providers`, `/dashboard/summary`, `/agents/{id}` and its  approve/deny/resume actions.- **AC2 — Allowed anonymous paths:** `/actuator/health` and `/actuator/info`  remain reachable without credentials when security is enabled.- **AC3 — Successful auth:** Requests presenting a valid configured key via  `Authorization: Bearer <key>` or `X-API-Key: <key>` reach the controller and  return the same payloads as today (no behavior change for authorized callers).- **AC4 — Wrong/absent/malformed credentials:** Requests with a missing header,  an unknown key, or a malformed header (e.g. bare `Bearer`) are rejected with  `401`; requests to authenticated routes never leak data in the error body.- **AC5 — Production fail-fast:** Starting with the `mariadb` profile (or  `app.security.enabled=true`) and no key configured aborts startup with a clear  error message; it is impossible to run a non-local profile with an open API.- **AC6 — Local dev default:** With the default/h2 profile and no explicit  override, the API behaves exactly as before (unauthenticated), so the existing  dashboard and local workflows keep working with no config change.- **AC7 — Config surface:** Keys are configurable via environment variables only  (`AUTH_API_KEYS` / `app.security.api-keys`), support plaintext and `sha256:`  hashed entries, and are never written to logs or returned by any endpoint.- **AC8 — CI smoke updated:** The `e2e-smoke` job sends credentials on all  authenticated curls AND asserts a `401` for an unauthenticated request to  `/api/v1/agents`. The suite is green.- **AC9 — Docs updated:** SECURITY.md no longer claims "no built-in  authentication/authorization"; it documents enabling, env vars, rotation, and  the recommendation to still front non-local deployments with a gateway.- **AC10 — No regression:** The full backend unit/integration/E2E suites pass  with auth disabled (default dev), and the new tests pass with auth enabled.  CORS behavior is unchanged when auth is disabled and does not weaken auth when  enabled.
## Error Handling
- **401 Unauthorized** — missing credential, unknown key, or malformed header on  a protected route. Response body is a consistent JSON error object (e.g.  `{"error":"unauthorized","message":"..."}`) with no stack traces or internal  detail. For the `Bearer` scheme, include `WWW-Authenticate: Bearer` on the  401 response.- **403 Forbidden** — reserved for a recognized-but-not-authorized credential if  finer-grained scopes are later added; not used in the initial shared-secret  model (any valid key is authorized). Kept in the response contract so clients  can distinguish "bad key" (401) from "not allowed" (403) later without a  breaking change.- **Startup failure (no key when required)** — application context fails to load  with a descriptive message such as *"Authentication is enabled  (app.security.enabled=true / mariadb profile) but no API key is configured.  Set AUTH_API_KEYS."* Fail-fast prevents any window where the service runs open  after a misconfiguration.- **Disabled-auth mode** — when `app.security.enabled=false`, the filter is inert  (bypasses all checks, zero overhead path) and no `401` is produced, matching  current behavior exactly.- **Secret hygiene** — configured keys/hashes are never logged (request logging,  audit, or exceptions), never exposed through any `/api/v1` read endpoint, and  compared in constant time to avoid timing side-channels. Any exception inside  the filter results in a `500` with a generic message; it must not fall through  to allow the request.- **Auditability** — rejected and accepted authentication attempts are recorded  via the existing audit/observability path (subject to its current  availability) with enough context to diagnose, but without the secret itself.
## Questions
- Q1: Which authentication mechanism should be implemented: a shared-secret API  key (`Bearer`/`X-API-Key`, stateless, recommended), or a full  username/password **session login with a dashboard login page** (larger scope,  needs a user store and UI work)? The issue leaves this open ("API key / Bearer  / session").- Q2: Should the default be **auth enabled by default** (breaking for anyone who  upgrades and runs the `mariadb` profile without configuring a key), or  **opt-in** with fail-fast only when explicitly enabled (recommended here)?- Q3: Which request surfaces count as "REST API" for this issue — only  `/api/v1/**` (recommended), or also the dashboard API module, the SSE/streaming  endpoints, and the MCP server? Should any of these be exempt (e.g. read-only  dashboard/telemetry)?- Q4: How should keys be provisioned and rotated — single shared key via env  (simplest), multiple keys with a key-id/hint for rotation (recommended), or  hashed-at-rest values with a key-management story?- Q5: Should sandboxed agents automatically receive the API key (via  `opencode.sandbox-env`, recommended) so agent-to-API calls are authenticated,  or should agent traffic stay unauthenticated for now?- Q6: Should the CI/e2e stacks run with auth **enabled** (test the real gate, as  proposed) or **disabled** (current behavior)? This affects how much of the  existing E2E suite must be updated to send credentials.
