# Spec — Add authentication/authorization to the REST API
- Source issue: `HappyLiang12/aria-conductor#1` (labels: `security`, `priority:P1`),  v0.2 hardening item.- Issue body: *"All `/api/v1/**` endpoints are currently unauthenticated. For any  non-local deployment the service must sit behind an authenticating gateway, or  gain built-in auth (API key / Bearer / session). Update the CI smoke test to send  credentials once auth lands. v0.2 hardening item; see SECURITY.md."*
## Problem Statement
Every endpoint under `/api/v1/**` in the Aria Conductor backend is currentlyunauthenticated. This is an explicit, documented trade-off for local evaluation(SECURITY.md → *Known Limitations*: "No built-in authentication/authorization"),but it means **any** process that can reach the service over a network — with nocredential of any kind — can:
- read, create, modify, and delete agents, workflows, runs, tools, and skills;- read and write knowledge items and review/promote knowledge;- read and update LLM provider credentials (API keys stored in the DB) and thereby  exfiltrate secrets;- trigger, approve, deny, resume, and cancel agent runs, including bypassing HITL /  approval-gate governance state;- mutate system configuration and, where `tools.shell.enabled` is on, cause  arbitrary tool/shell invocations through the agent execution path.
Because there is no identity or trust boundary today, a single exposed deploymentcompromises the entire control plane. SECURITY.md currently tells operators to placethe service behind their own authenticating gateway/reverse proxy, or keep it on atrusted local network; it also notes Docker binds to `127.0.0.1` by default. Thev0.2 hardening goal (per the issue) is that a non-local deployment can be brought up**only** with authentication in force, and that the CI smoke test verifies the newcredential requirement rather than the current open-API behavior.
Today `.github/workflows/ci.yml` (`e2e-smoke` job) curls `/actuator/health`,`/api/v1/agents`, `/api/v1/dashboard/summary`, `/api/v1/workflows`, and`/api/v1/knowledge?type=WORKFLOW` with **no** credentials via the composite`.github/actions/start-stack` action (which boots the jar with`--spring.profiles.active=h2`). Those curls silently assert the insecure state andmust be updated to prove auth is enforced.
A secondary gap: agents that run inside the sandbox (e.g. SDD/dev agents calling backinto the control-plane REST API) have no way to authenticate either, because nocredential material is provisioned to them. The backend already injects env vars intoevery agent sandbox via `opencode.sandbox-env` (`application.yml`), so there is anestablished mechanism to carry a credential.
The fix must not regress local single-user development: the default developerexperience (`h2` profile, which is the active profile in CI and local runs) shouldstay zero-friction, while non-local deployments are locked down.
## Proposed Solution
Add a **built-in authentication layer** to the backend in front of all `/api/v1/**routes, plus configuration, credential provisioning to sandboxed agents, docs, andupdated CI smoke coverage.
The recommended mechanism (see **Questions** Q1) is a lightweight **shared-secretAPI key** presented via `Authorization: Bearer <key>` or `X-API-Key: <key>`,implemented as a servlet filter / Spring Security `SecurityFilterChain` /`OncePerRequestFilter` registered before the controllers. It is intentionallystateless (no session store, no user table) and matches the current single-operator /single-node deployment model. A full username/password session login with adashboard login page, or per-user roles/scopes, is explicitly out of scope for thisissue unless maintainers choose otherwise (Q1, Q4).
Concretely:
1. **Auth filter + matcher**   - Protect all `/api/v1/**` routes with a single security chain / filter applied     app-wide (`act-app`).   - Allow anonymous, with **no** credential and **no** `WWW-Authenticate` demand,     only: `/actuator/health`, `/actuator/info` (the only exposed actuator     endpoints per `management.endpoints.web.exposure.include`), and the     non-`/api/v1` static/error surfaces. Everything under `/api/v1/**` requires a     valid credential.   - H2-console and dev-SQL surfaces stay gated exactly as today (loaded only under     the `h2` dev profile; not loaded in the `mariadb` profile).
2. **Configuration (env-driven, no secrets in source)**   - New property `app.security.enabled` (env `APP_SECURITY_ENABLED`).   - New property `app.security.api-keys` (env `AUTH_API_KEYS`) — a comma/whitespace     separated list of plaintext keys and/or hex SHA-256 hashes (entries prefixed     `sha256:`). Storing only hashes at rest is preferred; plaintext env is accepted     for operability but must never be logged or echoed.   - Defaults:     - `mariadb` (production/non-local) profile → `app.security.enabled=true` by       default; startup **fails fast** if no key is configured (see Error Handling).     - default/`h2` (local dev) profile → `app.security.enabled=false` unless       explicitly overridden, preserving the current zero-friction local UX and the       current CI `start-stack` behavior (Q6 governs whether CI/E2E runs auth       enabled).   - Auth must never weaken existing CORS behavior (`app.cors.allowed-origins`,     credentials handling).
3. **Credential check**   - Accept the key from `Authorization: Bearer <key>` or `X-API-Key: <key>`.   - Compare in constant time against the configured set (hash-compare against the     `sha256:` digest when hashed entries are configured).   - On success, mark the request authenticated and carry a non-secret hint (e.g.     first/last 4 chars of the matched key or its index) for audit logging; do not     invent user roles or scopes.
4. **Provisioning to agents / sandboxes**   - Expose the configured key to agent sandboxes through the existing     `opencode.sandbox-env` mechanism (e.g. an `ARIA_API_KEY`-style environment     variable) so sandboxed agents can call the API authenticated. When auth is     disabled or no key is configured, the variable is not injected.
5. **Docs**   - Update SECURITY.md *Known Limitations* to remove the "No built-in     authentication/authorization" claim and document: how to enable, env vars,     key rotation (restart to rotate a single key; add-then-remove for multi-key),     and the continuing recommendation to still front non-local deployments with an     authenticating gateway / restrict network exposure.   - Update `.env.example` with the new (blank/`change-me`) auth vars.
6. **CI smoke test**   - In `.github/workflows/ci.yml` `e2e-smoke`, configure a test key for the stack     (via env through `.github/actions/start-stack`) and add     `Authorization: Bearer <test-key>` to the existing authenticated curls     (`/api/v1/agents`, `/api/v1/dashboard/summary`, `/api/v1/workflows`,     `/api/v1/knowledge?type=WORKFLOW`).   - Add a negative check: calling `/api/v1/agents` **without** credentials must     return `401`, proving auth is enforced (Q6 governs whether the whole E2E stack     runs with auth enabled).
## Acceptance Criteria
- **AC1 — Enforcement:** With `app.security.enabled=true`, every `/api/v1/**`  request that presents no valid credential returns `401 Unauthorized` and no  handler/business logic runs for the request. Verified by automated tests (mock  MVC + at least one live boot test) across a representative sample of controllers:  `/agents`, `/agents/{id}` and its approve/deny/resume actions, `/workflows`,  `/runs`, `/tools`, `/skills`, `/knowledge`, `/llm-providers`,  `/dashboard/summary`.- **AC2 — Allowed anonymous paths:** `/actuator/health` and `/actuator/info` remain  reachable without credentials when security is enabled (no `401`, no  `WWW-Authenticate` demand).- **AC3 — Successful auth:** Requests presenting a valid configured key via  `Authorization: Bearer <key>` or `X-API-Key: <key>` reach the controller and  return the same payloads/status as today (no behavior change for authorized  callers).- **AC4 — Wrong/absent/malformed credentials:** Missing header, unknown key, or  malformed header (e.g. bare `Bearer`, non-hex or malformed `sha256:` entry, empty  value) are rejected with `401`; protected routes never leak data or internals in  the error body.- **AC5 — Production fail-fast:** Starting with the `mariadb` profile (or otherwise  with `app.security.enabled=true`) and no key configured aborts startup with a  clear, actionable error; it is impossible to run a non-local profile with an open  API.- **AC6 — Local dev default:** With the default/`h2` profile and no explicit  override, the API behaves exactly as before (unauthenticated); the existing  dashboard and local workflows keep working with no config change.- **AC7 — Config surface:** Keys are configurable via environment variables only  (`AUTH_API_KEYS` / `APP_SECURITY_ENABLED`, mapped from `app.security.*`),  support plaintext and `sha256:`-hashed entries, and are never written to logs or  returned by any endpoint.- **AC8 — CI smoke updated:** The `e2e-smoke` job sends credentials on all  authenticated curls **and** asserts a `401` for an unauthenticated request to  `/api/v1/agents`. The suite is green.- **AC9 — Docs updated:** SECURITY.md no longer claims "no built-in  authentication/authorization"; it documents enabling, env vars, rotation, and the  recommendation to still front non-local deployments with a gateway. `.env.example`  carries the new vars.- **AC10 — No regression:** The full backend unit/integration/E2E suites pass with  auth disabled (default dev), and the new auth tests pass with auth enabled. CORS  behavior is unchanged when auth is disabled and is not weakened when auth is  enabled.
## Error Handling
- **401 Unauthorized** — missing credential, unknown key, or malformed credential on  a protected route. Response body is a consistent JSON error object (e.g.  `{"error":"unauthorized","message":"..."}`) with no stack traces or internal  detail. For the `Bearer` scheme, include `WWW-Authenticate: Bearer` on the `401`  response so clients can prompt/retry correctly.- **403 Forbidden** — reserved for a recognized-but-not-authorized credential should  finer-grained scopes/roles be added later; not produced in the initial  shared-secret model (any valid key is authorized). Kept in the response contract so  clients can later distinguish "bad key" (`401`) from "not allowed" (`403`)  without a breaking change.- **Startup failure (auth required, no key)** — application context fails to load  with a descriptive message such as *"Authentication is enabled  (app.security.enabled=true / mariadb profile) but no API key is configured. Set  AUTH_API_KEYS."* Fail-fast prevents any window in which the service runs open  after a misconfiguration.- **Disabled-auth mode** — when `app.security.enabled=false`, the filter/chain is  inert (bypasses all checks with a zero-overhead path) and never emits `401`,  exactly matching current behavior.- **Secret hygiene** — configured keys/hashes are never logged (request logging,  audit, or exceptions), never exposed through any `/api/v1` read endpoint, and are  compared in constant time to avoid timing side-channels. Any unexpected exception  inside the filter results in a `500` with a generic message and **must not** fall  through and allow the request.- **Auditability** — rejected and accepted authentication attempts are recorded via  the existing audit/observability path with enough context to diagnose (timestamp,  path, key hint) but never with the secret itself.
## Questions
- Q1: Which authentication mechanism should be implemented: a shared-secret API key  (`Bearer`/`X-API-Key`, stateless — recommended), or a full username/password  **session login with a dashboard login page** (larger scope; needs a user store and  UI work)? The issue leaves it open ("API key / Bearer / session").- Q2: Should this ship as **built-in app auth**, **gateway-only** (documentation/  deployment change, no code), or **both** (built-in auth plus a documented  recommendation to still front non-local deployments with a gateway)? The issue  says "must sit behind an authenticating gateway, **or** gain built-in auth".- Q3: Should auth be **enabled by default** for the `mariadb`/production profile  (breaking for anyone upgrading without configuring a key, but locked down by  default — recommended), or **opt-in** with fail-fast only when explicitly enabled  or on the production profile?- Q4: How should keys be provisioned and rotated — a single shared key via env  (simplest), or multiple keys (allowing add-new-then-remove-old rotation,  recommended)? Should only hashes (`sha256:`) be accepted, or also plaintext env  keys for operability?- Q5: Should sandboxed agents automatically receive the API key via the existing  `opencode.sandbox-env` mechanism (recommended) so agent-to-API calls are  authenticated, or should agent traffic stay unauthenticated for now?- Q6: Should the CI/E2E smoke stack run with auth **enabled** (proving the real gate,  as proposed in AC8) or **disabled** (current behavior, with the new auth coverage  left to unit/integration tests)? This determines how much of the existing E2E suite  must send credentials.
