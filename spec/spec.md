# Spec — [security] Add authentication/authorization to the REST API
- Source issue: `#1` (`HappyLiang12/aria-conductor`), labels `security`, `priority:P1`,  milestone `v0.2 hardening`.- Issue body: *"All `/api/v1/**` endpoints are currently unauthenticated. For any  non-local deployment the service must sit behind an authenticating gateway, or  gain built-in auth (API key / Bearer / session). Update the CI smoke test to send  credentials once auth lands. v0.2 hardening item; see SECURITY.md."*
## Problem Statement
Every endpoint under `/api/v1/**` in the Aria Conductor backend is currentlyunauthenticated. This is an explicit, documented trade-off for local evaluation(SECURITY.md → *Known Limitations*), but it means **any** process that can reachthe service over a network can, with no credential:
- read, create, modify, and delete agents, tools, skills, workflows, and runs;- read and write knowledge items and review/promote knowledge;- manage LLM provider credentials (including API keys stored in the DB) and  thereby exfiltrate secrets;- trigger, approve, deny, and cancel agent runs and change governance/approval  state (including bypassing HITL approval gates);- mutate system configuration and issue arbitrary tool/shell invocations through  the agent execution path.
Because there is no identity or trust boundary today, a single exposed deploymentcompromises the entire control plane. The v0.2 hardening goal (SECURITY.md)requires that a non-local deployment cannot be brought up with an open API, andthat the CI smoke test verifies the new credential requirement rather than thecurrent "no auth" behavior. Today `.github/workflows/ci.yml` (`e2e-smoke` job)curls `/api/v1/agents`, `/api/v1/dashboard/summary`, `/api/v1/workflows`, and`/api/v1/knowledge` with **no** credentials, which silently asserts the insecurestate.
A secondary gap: agents that run inside the sandbox and call back into the API(e.g. SDD/dev agents using `gh`/`curl`/HTTP against the control plane) have no wayto authenticate either, because no credential material is provisioned to them.
The fix must not regress local single-user development: the default developerexperience should stay zero-friction while non-local deployments are locked down.
## Proposed Solution
Add a **built-in authentication layer** to the backend in front of all`/api/v1/**` routes, plus configuration, a small credential-provisioning path forsandboxed agents, docs, and updated CI smoke coverage. The default must remainzero-friction for local development while being locked down for non-localdeployments.
The recommended mechanism (see **Questions** Q1) is a lightweight **shared-secretAPI key** presented via `Authorization: Bearer <key>` or `X-API-Key: <key>`,implemented as a servlet filter / `OncePerRequestFilter` (Spring Security`SecurityFilterChain`) registered before the controllers. It is intentionallystateless (no session store, no user table) and matches the current singleoperator / single node deployment model. A full username/password session loginwith a dashboard login page is explicitly out of scope unless maintainers chooseotherwise (Q1).
Concretely:
1. **Auth filter + matcher**   - Protect all `/api/v1/**` routes with a single filter/security chain applied     app-wide (`act-app`).   - Allow anonymous, with **no** `WWW-Authenticate` demand, only the health/info     actuator endpoints (`/actuator/health`, `/actuator/info`) and     non-`/api/v1` static/error surfaces. Everything under `/api/v1/**` requires a     valid credential.   - H2/dev-only surfaces remain gated to their existing profiles as today.
2. **Configuration (env-driven, no secrets in code)**   - New property `app.security.enabled` (env `APP_SECURITY_ENABLED`).   - New property `app.security.api-keys` (env `AUTH_API_KEYS`) — a comma/space     separated list of plaintext keys and/or hex SHA-256 hashes (entries prefixed     `sha256:`). Storing only hashes at rest is preferred; plaintext env is     accepted for operability but must never be logged or echoed.   - Defaults:     - `mariadb` (production) profile → `app.security.enabled=true`; startup       **fails fast** if no key is configured (see Error Handling).     - default/`h2` (local dev) profile → `app.security.enabled=false` unless       explicitly overridden, preserving the current local UX.   - Auth must never weaken CORS behavior.
3. **Credential check**   - Accept the key from `Authorization: Bearer <key>` or `X-API-Key: <key>`.   - Compare in constant time against the configured set (hash compare when     `sha256:` hashes are configured).   - On success, set a lightweight request attribute/principal (e.g.     `authenticated` + key hint) for audit logging; do not invent user roles or     scopes.
4. **Provisioning to agents / sandboxes**   - Expose the generated key to agent sandboxes via the existing sandbox-env /     `opencode.sandbox-env` mechanism (e.g. an `ARIA_API_KEY`-style environment     variable) so sandboxed agents can call the API authenticated. When no key is     configured (auth disabled), the variable is not injected.
5. **Docs**   - Update SECURITY.md *Known Limitations* to remove the "no built-in auth"     claim and document configuration, key rotation, and the recommendation to     still front non-local deployments with an authenticating gateway.
6. **CI smoke test**   - In `.github/workflows/ci.yml` `e2e-smoke`, configure a test key for the stack     and add `Authorization: Bearer <test-key>` to the existing authenticated     curls (`/api/v1/agents`, `/api/v1/dashboard/summary`, `/api/v1/workflows`,     `/api/v1/knowledge`).   - Add a negative check: calling `/api/v1/agents` **without** credentials must     return `401`, proving auth is enforced (Q6 governs whether the whole E2E     suite runs with auth enabled).
## Acceptance Criteria
- **AC1 — Enforcement:** With `app.security.enabled=true`, every `/api/v1/**`  request that presents no valid credential returns `401 Unauthorized` and no  handler logic runs. Verified by automated tests (mock MVC + a live boot test)  across a representative sample of controllers: `/agents`, `/workflows`, `/runs`,  `/tools`, `/skills`, `/knowledge`, `/llm-providers`, `/dashboard/summary`,  `/agents/{id}` and its approve/deny/resume actions.- **AC2 — Allowed anonymous paths:** `/actuator/health` and `/actuator/info`  remain reachable without credentials when security is enabled.- **AC3 — Successful auth:** Requests presenting a valid configured key via  `Authorization: Bearer <key>` or `X-API-Key: <key>` reach the controller and  return the same payloads as today (no behavior change for authorized callers).- **AC4 — Wrong/absent/malformed credentials:** Missing header, unknown key, or  malformed header (e.g. bare `Bearer`, non-hex hash entry) are rejected with  `401`; protected routes never leak data in the error body.- **AC5 — Production fail-fast:** Starting with the `mariadb` profile (or with  `app.security.enabled=true`) and no key configured aborts startup with a clear  error message; it is impossible to run a non-local profile with an open API.- **AC6 — Local dev default:** With the default/`h2` profile and no explicit  override, the API behaves exactly as before (unauthenticated); the existing  dashboard and local workflows keep working with no config change.- **AC7 — Config surface:** Keys are configurable via environment variables only  (`AUTH_API_KEYS` / `app.security.api-keys`), support plaintext and `sha256:`  hashed entries, and are never written to logs or returned by any endpoint.- **AC8 — CI smoke updated:** The `e2e-smoke` job sends credentials on all  authenticated curls **and** asserts a `401` for an unauthenticated request to  `/api/v1/agents`. The suite is green.- **AC9 — Docs updated:** SECURITY.md no longer claims "no built-in  authentication/authorization"; it documents enabling, env vars, rotation, and  the recommendation to still front non-local deployments with a gateway.- **AC10 — No regression:** The full backend unit/integration/E2E suites pass with  auth disabled (default dev), and the new tests pass with auth enabled. CORS  behavior is unchanged when auth is disabled and does not weaken auth when  enabled.
## Error Handling
- **401 Unauthorized** — missing credential, unknown key, or malformed header on a  protected route. Response body is a consistent JSON error object (e.g.  `{"error":"unauthorized","message":"..."}`) with no stack traces or internal  detail. For the `Bearer` scheme, include `WWW-Authenticate: Bearer` on the 401  response.- **403 Forbidden** — reserved for a recognized-but-not-authorized credential if  finer-grained scopes are later added; not used in the initial shared-secret  model (any valid key is authorized). Kept in the response contract so clients  can distinguish "bad key" (`401`) from "not allowed" (`403`) later without a  breaking change.- **Startup failure (no key when required)** — application context fails to load  with a descriptive message such as *"Authentication is enabled  (app.security.enabled=true / mariadb profile) but no API key is configured. Set  AUTH_API_KEYS."* Fail-fast prevents any window in which the service runs open  after a misconfiguration.- **Disabled-auth mode** — when `app.security.enabled=false`, the filter is inert  (bypasses all checks, zero-overhead path) and produces no `401`, matching  current behavior exactly.- **Secret hygiene** — configured keys/hashes are never logged (request logging,  audit, or exceptions), never exposed through any `/api/v1` read endpoint, and  are compared in constant time to avoid timing side-channels. Any exception  inside the filter results in a `500` with a generic message; it must not fall  through and allow the request.- **Auditability** — rejected and accepted authentication attempts are recorded  via the existing audit/observability path (subject to its current availability)  with enough context to diagnose, but never with the secret itself.
## Questions
- Q1: Which authentication mechanism should be implemented: a shared-secret API  key (`Bearer`/`X-API-Key`, stateless, recommended), or a full username/password  **session login with a dashboard login page** (larger scope; needs a user store  and UI work)? The issue leaves this open ("API key / Bearer / session").- Q2: Should auth be **enabled by default** for the `mariadb`/production profile  (breaking for anyone upgrading without configuring a key), or **opt-in** with  fail-fast only when explicitly enabled or on the production profile  (recommended)?- Q3: Which request surfaces count as "REST API" for this issue — only  `/api/v1/**` (recommended), or also dashboard-API/SSE-streaming endpoints and  the MCP server? Should any surface be exempt (e.g. read-only  dashboard/telemetry)?- Q4: How should keys be provisioned and rotated — a single shared key via env  (simplest), multiple keys with a key hint/id for rotation (recommended), or  hashed-at-rest values with a key-management story?- Q5: Should sandboxed agents automatically receive the API key (via the existing  sandbox-env mechanism, recommended) so agent-to-API calls are authenticated, or  should agent traffic stay unauthenticated for now?- Q6: Should the CI/E2E stacks run with auth **enabled** (testing the real gate,  as proposed) or **disabled** (current behavior)? This determines how much of the  existing E2E suite must be updated to send credentials.
