# Spec: Issue `#qoder-regression` analysis cannot be grounded — unresolvable issue reference in SDD request path
Status: Draft for reviewSpec target repo: `HappyLiang12/aria-conductor` (assumed; see Questions)Related fixture knowledge attached to this task: `e2e-skill-source-1788602862343-340` (PROMPT), `e2e-shared-guideline-1788602862027-198`, `e2e-knowledge-race-6-1788602842593-1876`, `e2e-knowledge-race-5-1788602842592-5111` (GUIDELINEs), `spec-25c9a96b-1277-42f3-a18c-46d8d87e6ef7` (SPEC: SDD spec).
## Problem Statement
A BA-agent (spec-authoring) task was dispatched with the instruction to "analyze issue`#qoder-regression`" and produce an authoritative spec at `/workspace/spec.md`. The issuebody was **not** included in the task message, and the prescribed retrieval command`gh issue view #qoder-regression -R {issueRepo}` cannot succeed for three independentreasons:
1. **Unresolvable issue handle.** The handle `#qoder-regression` is non-numeric. The GitHub   CLI (`gh issue view`) only accepts a numeric issue number or an issue URL; it rejects   `#qoder-regression` outright with `invalid issue format`. Therefore the handle cannot be   resolved against any repository.2. **Unset repository placeholder.** The command template references `{issueRepo}`, which was   never substituted with a concrete `owner/repo`. Without it, no repository can be queried.3. **No matching issue exists in the accessible accounts/repositories.** Exhaustive search   (all issues, open and closed, across every repository reachable with the configured   `GH_TOKEN`) found no issue whose title, body, or labels correspond to `qoder-regression`,   and no repository named `qoder*` under the authenticated account.
Consequently, the BA agent receives only the generic task template plus a set of Phase-E e2efixture knowledge items (an `e2e-skill-source` prompt and `e2e-shared-guideline` /`e2e-knowledge-race-*` guidelines) that carry no statement of the defect. There is noauthoritative statement of the desired behavior change anywhere in the task context.
This is a **reproducible regression in the SDD natural-flow request-construction path**: aspec-writing sub-task is emitted with an unresolved/placeholder issue reference and anun-substituted `{issueRepo}` parameter, and the sub-agent is told to fetch a body that theorchestrator never supplied. The observable symptom in this run: the BA agent cannot obtainany facts about the issue and therefore cannot produce a grounded Problem Statement,Proposed Solution, or Acceptance Criteria for the intended change.
Out of scope: any inference about a specific product defect. Because no issue body exists,any concrete bug description written here would be fabricated; this spec therefore scopes thefix to the request-construction defect that is directly observable in this run.
## Proposed Solution
Fix the SDD natural-flow dispatch layer so that a BA/spec-authoring sub-task is never emittedwith an unfetchable issue reference. Concretely:
1. **Resolve the issue reference before dispatch.** When the orchestrator composes a   spec-authoring task, it must substitute both parameters:   - the concrete `{issueRepo}` (`owner/repo`) of the governing repository, and   - a real issue identifier (numeric number or full URL), resolved from the internal issue     tracker/DB before the task message is built.   Dispatch must be **aborted** (fail-fast) if either value is empty at message-build time.
2. **Inline the authoritative issue body.** The task message to the BA agent must embed the   full issue `title`, `body`, and `labels` (equivalent to the output of   `gh issue view <number> -R <owner/repo> --json title,body,labels`) rather than relying on   the sub-agent to fetch it. This removes the dependency on `gh` availability and network   access inside the sandbox and removes ambiguity about which repository is authoritative.
3. **Validate the handle format.** Any user- or template-supplied issue key of the form   `#<slug>` that is not a numeric number must be mapped to a concrete issue via the   repository's issue list/search before it is accepted; if no match exists, the task is   failed early with an explicit "issue not found" error instead of being dispatched.
4. **Seed meaningful knowledge context.** If e2e/QA fixture knowledge items are attached to a   spec-authoring task, include their content (not only their names/IDs) so the BA agent can   use them; or, when they are unrelated to the target issue, omit them from the context.
5. **Observability.** Emit a structured, machine-readable record (task ID, resolved   `issueRepo`, resolved issue number, and a hash of the inlined body) so a downstream QA/audit   step can verify every spec task carried a grounded issue reference.
## Acceptance Criteria
- [ ] A spec-authoring task is only dispatched after `{issueRepo}` has been substituted with a      valid `owner/repo` and the issue reference has been resolved to a numeric issue number or      URL that exists in that repository.- [ ] The BA task message includes the full issue `title`, `body`, and `labels` inline; a fresh      BA-agent run can complete without invoking `gh`.- [ ] Attempting to dispatch a task for a non-numeric/unresolvable issue key (e.g.      `#qoder-regression` with no matching issue) fails fast with an explicit error that names      the issue key and the repository, and does **not** emit a task for the BA agent.- [ ] Attempting to dispatch with an empty `{issueRepo}` fails fast with an explicit error.- [ ] When fixture knowledge items (e.g. `e2e-skill-source-*`, `e2e-shared-guideline-*`,      `e2e-knowledge-race-*`) are attached to a spec task, their full content is present in the      task context or they are filtered out as unrelated; names-only attachments no longer occur.- [ ] The dispatch layer records task ID, resolved repository, resolved issue number, and a body      hash for every spec task (audit/observability requirement).- [ ] A regression test covers: (a) unresolvable slug → fail-fast, (b) empty repo → fail-fast,      (c) happy path → issue body inlined into the message.
## Error Handling
- **Unresolvable issue key (`invalid issue format`, no match in repo):** do not dispatch.  Return a 4xx-class error (or equivalent structured failure) naming the offending key and the  repository searched. Message: `Issue "<key>" could not be resolved in <owner/repo>; expected a  numeric issue number or an existing issue URL.`- **Un-substituted `{issueRepo}` / empty repository parameter:** do not dispatch. Return an  explicit configuration error identifying the missing parameter.- **Issue exists but body is empty:** dispatch is still permitted, but the task message must  state `body: (empty)` explicitly so the BA agent can surface the gap via the spec's Questions  section rather than silently proceeding without context.- **Repository or issue not visible to the configured token:** treat as not-found (do not leak  existence); the failure message must distinguish "not found / no permission" from  "transient fetch failure" only in internal audit logs, not in the user-facing error.- **Transient fetch failure (network/API):** retry with bounded exponential backoff (e.g. up to  3 attempts), then fail the dispatch with the last error surfaced to the orchestrator; never  fall back to dispatching an ungrounded task.- **BA agent still reports missing context:** the spec-authoring prompt must instruct the agent  that, if the issue body is absent after all of the above, it must record every missing fact in  the spec's `## Questions` section and must not invent product behavior.
